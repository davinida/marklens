## 1. 요청

### 1-1. 브라우저 API

`POST /api/search/v2?top_k=1..20` (기본 5)

헤더:

| 헤더 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `X-Turnstile-Token` | string | 예 | 5분 내 발급된 1회용 토큰(v1 과 같음). 상표명 확인 패널의 토큰과 재사용하지 않는다 |

`multipart/form-data` 본문 — **세 입력 중 하나 이상**:

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `image` | PNG/JPEG/WebP, 최대 10 MiB, 32..4096px | 셋 중 하나 이상 | v1 `file` 과 같은 검증(413/415/400). 수동 크롭 결과를 그대로 보낸다 |
| `name` | string | 〃 | 상표명. 보이지 않는 서식 문자(유니코드 Cf — 폭 없는 공백·BOM·부드러운 붙임표·양방향 제어 문자 등)를 지우고 NFC 로 맞춘 뒤 앞뒤 공백을 떼고 1..100자(공백·서식 문자만이면 없는 것으로 본다 — 2026-11-23 부터, `pair_axes.clean_input_name`; 상표명 확인·발음·관념 검색도 같은 정리. 중계 BFF 의 100자 검사와 화면의 검색 버튼도 같은 규칙의 TS 구현 `frontend/lib/markName.ts` 뒤에 센다 — 두 구현이 같은 결과인지는 공용 사례 `shared/text/clean_input_name_cases.json` 으로 pytest·Vitest 가 본다). NFKC·대소문자 정규화는 서버가 한다 |
| `goods_codes` | string, **반복 필드**(`goods_codes=G0502&goods_codes=S120602`) 또는 쉼표로 이은 1개 | 〃 | 유사군 코드 `^[GS][0-9]{4,6}$`, 대소문자 무시, 중복 제거, 최대 60개(프론트-6 선택 20개의 유사군 합집합 `goodsCodeUnion`) |
| `type_override` | `문자` \| `도형` \| `결합` | 아니오 | 사용자가 결과 화면에서 유형을 고쳐 다시 요청할 때. 있으면 `query_type.source = "user"` |

BFF 는 이 순서로 처리한다: `content-length` 상한(10 MiB + 1 MiB) → `top_k` 검증(422) → Turnstile
검증(403/503/504) → 폼 파싱(400) → `image` 크기·MIME(413/415) → `name`·`goods_codes`·`type_override` 형식(422) → 세 입력이
모두 비면 400 → 토큰을 떼고 내부 `POST /search/v2?top_k=`로 **같은 필드 이름**으로 전달 → 응답 본문·상태를 그대로 돌려준다
(`safeResponseHeaders`). 이미지 URL 은 응답에 `/api/images/...` 로 들어 있으므로 BFF 가 바꾸지 않는다.

### 1-2. 내부 API

`POST /search/v2?top_k=1..20` — 필드·검증은 1-1 과 같다. 추가 검증: `image` 는 v1 과 같은 디코딩·치수 검사, `goods_codes` 는
정규식·개수, `type_override` 는 열거값. 세 입력이 모두 없으면 **400** `{"detail": "image, name, goods_codes 중 하나는 있어야
합니다."}`(§5-1). 한도는 `MARKLENS_SEARCH_RATELIMIT`(한 IP 10/minute, 한도 묶음 `search`).

### 1-3. 입력 조합 → 계산되는 축·후보 풀·유형 출처

| 입력 | 계산되는 축 | 후보 풀(합집합, 출원번호로 중복 제거) | `query_type.source` |
|---|---|---|---|
| 이미지만 | `x2_img` | CLIP 코사인 상위 20(v1 `scoring_k`) | `ocr`(도형계: 글자 영역 ≥ 0.05 면 결합-도형요부, 읽은 글자는 `suggested_name`; 실패 시 `fallback` → 도형). 이름 없는 판단(`risk.pattern` `noname:x2_whole`, v1.4) |
| 이미지 + 지정상품 | `x2_img`·`x4` | 위 ∪ 유사군이 겹치는 DB 상표 상위 20 | 위와 같음. 이름 없는 판단(`noname:x2_whole+x4`) |
| 이름만 | `x1`·`x2_text`·`x3`(게이트) | 발음 상위 20 ∪ 철자 상위 20 ∪ 관념 상위 5(하한 0.55) | `fallback` → 문자 |
| 이름 + 지정상품 | 위 + `x4` | 위 ∪ 유사군이 겹치는 DB 상표 상위 20(자카드 순) | `fallback` → 문자 |
| 이미지 + 이름(+ 지정상품) | 전부 | 위 전부 | `ocr`(fig_ratio 로 문자/결합-문자요부 — 이름이 있으면 항상 문자계; 실패 시 `fallback` → 문자). 질의 이미지가 사진이면 이름 있는 판단의 `x2_img` 를 관측 없음으로(§2-4 7항) |
| 지정상품만 | `x4` | 유사군이 겹치는 DB 상표 상위 20 | `fallback` → 문자 (caveat `GOODS_ONLY`) |

후보 풀의 크기는 `meta.pool` 로 돌려준다. 풀을 합친 뒤 후보마다 축을 계산하고(§2-2 `axes`), `risk_score` 로 위험도를 낸 다음
**정렬 위치 내림차순**(동점은 `x2_img` 내림차순 → 출원번호 오름차순)으로 정렬해 `top_k` 개를 돌려준다. 정렬 위치 = (위험도 p 로
정한 등급, 그 등급 안 위치 (p − 그 등급 하한) ÷ (다음 하한 − 그 등급 하한)) — 하한은 그 판단의 계수 집합 것(이름 없는 판단은
`meta.thresholds.nameless[pattern]`). 같은 계수 집합만 있는 응답에서는 **위험도 내림차순과 같다**(2026-11-20 전 정렬과 같음 —
엔진 테스트로 고정). 이름 있는 판단과 이름 없는 판단(이름 없는 후보·`nameless_floor`·`goods_floor`)이 섞이면 위험도 눈금이 달라
p 대신 이 위치로 견준다. 판단을 둘 이상 계산한 후보(`nameless_floor`·`goods_floor` 비교)는 그 가운데 높은 위치에 둔다. 단독·도형
규칙으로 표시 등급만 올라간 후보도 p 자리에 둔다. 정렬 기준은 CLIP 유사도가 아니다. 발음·철자 풀은
유사도 0 인 후보를 넣지 않는다.

### 2-4. 등급 규칙(요약 — 정본은 통합 모델 설계 §7-2)

1. `prob = sigmoid(intercept + Σ 계수×값)`. 계수 집합은 입력의 결측 패턴(이미지 유무 × 상품 유무, v1.3 §7-3)에 따라 넷 중 하나 —
   관측된 축만 입력에 있고 결측 지시변수는 없다(관념 축이 null 이면 값 0). 축 하나를 하한값(현실 분포 비유사 쌍 평균: 이미지
   0.3487·상품 0.0252) 이상으로 더 관측하면 `prob` 는 내려가지 않는다(결합 제약, 적재 때 검증). 유형은 `overall.query_type.type`
   하나를 쌍 전체에 쓴다(학습이 이 사건 표장의 유형으로 했으므로). v1.4: 호칭·철자가 둘 다 결측이고 이미지가 있으면 이름 없는
   계수 집합(이미지만 `noname:x2_whole` / 이미지+상품 `noname:x2_whole+x4`, 설계 §7-4) — 이름 없는 입력에 후보와 같은 이름을
   더하면 위험도가 내려가지 않는다(결합 제약 `same_name`, 적재 때 검증). v1.4.5: 이름 없는 이미지+업종 집합은 로고 유사도 × 업종
   겹침의 곱하기 항(`x2_whole×x4`·`x2_whole×도형계×x4`)이 있어 업종의 효과가 로고가 닮은 만큼만 생긴다. 이 집합은 상품을 더
   관측할 때의 결합 제약 대신 "업종 겹침 0 이면 이미지만 판단 이하"(JSON `goods_rule` `no_raise_without_overlap`, 적재 때 검증)를
   지키고, 겹침이 하한 이상일 때 등급이 이미지만 아래로 내려가지 않는 것은 8항 업종 하한이 맡는다(통합 모델 설계 §7-12).
2. `grade` 는 그 판단의 하한으로. 이름 있는 판단은 `meta.thresholds.grade` — 0.5902 이상 위험, 0.5059 이상 검토 권장, 0.0902
   이상 주의, 그 아래 안전(검토 권장은 2026-11-23 실제 검색 기준 — 그 전 0.1805; 주의·위험은 v1.3 그대로, 위험은 정밀도 0.8 목표 미달 대체값). 이름 없는 판단은
   `meta.thresholds.nameless[pattern]` — 실제 검색 기준(2026-11-20, 설계 §7-4-4): 심사를 거치지 않은 표장(정답 데이터의
   거절결정불복 출원 표장·권리범위확인 확인대상표장 중 DB 에 없는 것)으로 검색한 후보 쌍에서, 이름 없는 판단이 그 등급 이상인
   비율이 같은 쌍을 이름을 알고 채점했을 때 그 등급 이상인 비율과 같아지는 위험도 — 이미지만 0.3677 / 0.491 / 0.5724(이미지
   유사도로 0.558 / 0.763 / 0.896), 이미지+상품은 v1.4.5 부터 이미지만과 같은 0.3677 / 0.491 / 0.5724(곱하기 항 계수로 같은 대조군을
   재 보니 목표 안이라 이미지만 기준 그대로 — 설계 §7-12; v1.4.3 까지 0.2944 / 0.4441 / 0.7892). null 인 등급은 위험도로는 닿지
   않는다(지금은 없음).
3. **단독 규칙**(97후3050 후단): 어느 축이든 τ 이상이면 등급 하한 "검토 권장"(자동 "위험" 아님) → `rule_triggers`.
4. **도형 규칙**(미검증 제품 규칙): 도형계 유형이면 `figure_caveat = true` + `caveats` 에 도형 문구, `x2_img ≥ 0.9` 면 등급 하한 "검토 권장".
5. 유형 규칙(2026-10-24 개정 — OCR 은 유형의 최종 결정자가 아니라 이름이 없을 때 글자를 찾아 주는 도우미):
   - `type_override` 가 있으면 그대로(`source: user`; `결합` 은 이름이 있을 때 결합-문자요부, 없을 때 결합-도형요부).
   - **`name` 이 있으면 유형은 항상 문자계**: 이미지가 없거나 OCR `fig_ratio < 0.08` → 문자, 그 외(이미지에 뚜렷한 도형
     영역) → 결합-문자요부. OCR 이 글자를 못 읽어도(실패·시간 초과·비활성) 도형계로 가지 않고 문자(`source: fallback`,
     caveat `OCR_FALLBACK`). 근거: 사용자가 이름을 입력했다 = 상표에 문자 부분이 있다, 판례상 문자가 있는 결합상표는 호칭이
     중요(97후3050). `source` 는 비율을 썼으면 `ocr`, 아니면 `fallback`.
   - **도형계(도형·결합-도형요부)는 두 경우만**: (a) `name` 없는 이미지 질의 — OCR 글자 영역 `text_ratio ≥ 0.05` 면
     결합-도형요부, 그 외·OCR 실패면 도형 (b) `type_override` 로 사용자가 직접 선택.
   - `name` 없는 이미지 질의에서 OCR 이 글자를 읽으면 `query_type.suggested_name`(확신도 ≥ 0.5 박스, 최대 60자)과
     caveat `NAME_SUGGESTED` 를 돌려준다. 못 읽으면 기존대로 도형 + `FIGURE_LOW_DATA`. 이 요청에서 이름 축을 자동
     계산하지는 않는다(사용자 확인 뒤 재요청 — Turnstile 토큰 1회용 규약).
   - 비고(개정 이유): 이전 규칙은 OCR 자동 유형(`auto_type`)이 최종 결정자여서, 글자가 작은 결합상표를 도형으로 오판하면
     (X2 설계 §7 유형 일치 76% — 오판 24%) 이름이 있어도 `x1×문자계` 교호작용(계수 2.26)이 빠져 호칭 가중치가 깎였다.
     셋 다 입력 실측(2026-10-24): 같은 "블루커피" / BLU hands 쌍이 이름만 넣으면 p 0.58(위험), 도형 이미지를 더하면 OCR 이
     도형으로 판정해 p 0.08(검토 권장)로 떨어졌다 → 이름이 있으면 문자계로 고정.
     개정 후 실측(2026-10-25): 같은 셋 다 입력이 결합-문자요부(OCR `fig_ratio` 0.717)로 판정돼 **p 0.47(검토 권장)** —
     `x1×문자계` 는 돌아왔고, 이름만(0.58 위험)과의 남은 차이는 유형이 아니라 이미지 결측 보정(`miss_x2img` +0.50 로짓)이
     실제 x2_img 0.36 의 기여(+0.08, 1.0 이어도 +0.21)보다 큰 v1.2.1 모델 성질이었다 → **통합 모델 v1.3(2026-10-25, 설계
     §7-3)** 이 결측 지시변수를 결측 패턴별 계수 집합 + 결합 제약으로 바꿔 닫았다: 같은 쌍 이름만 p 0.530, 셋 다(x2_img 0.36)
     0.531 — 입력을 더 주면 위험도가 내려가지 않는다(둘 다 검토 권장; 위험 하한 0.5902).
6. **이름 없는 판단과 견주기**(v1.4, 2026-11-20; 그 밖의 이름 + 이미지 질의는 v1.4.2, 2026-11-23): 이름과 이미지가 있는 질의에서
   후보마다 이름 있는 판단과 이름 없는 판단의 등급을 견주어 높은 쪽을 쓴다(같으면 이름 있는 쪽, 정렬 위치는 둘 중 높은 쪽). 이름 없는
   쪽이 쓰이면 `rule_triggers` 에 `nameless_floor`, `prob`·기여도·`pattern` 은 그쪽 것. 견주는 판단은 질의에 따라 다르다.
   - `type_override` 로 유형을 도형계로 고친 질의(v1.4): **같은 입력에서 이름을 뺀 판단**(이름 없는 계수 집합 — 업종이 있으면
     이미지+상품, 8항 업종 하한을 적용한 뒤의 판단). 사용자가 "도형이 요부"라고 고친 경우다.
   - 그 밖의 질의(자동 유형 — 이름이 있으면 문자계 — 와 문자계로 고친 질의), 계수 JSON 이 `logo_floor` 를 켤 때(v1.4.2): **이름도
     업종도 뺀 이미지만 판단**(`noname:x2_whole` — 지금 계수·기준 그대로; 유형은 이름 없이 넣었을 때 받을 유형 — 자동이면 OCR 글자
     영역 ≥ 0.05 면 결합-도형요부, 그 밖·실패면 도형, 사용자가 고친 유형이면 이름 없이 고른 것과 같게). 업종이 들어간 이름 없는
     판단은 쓰지 않는다(업종만 겹친 무관한 로고가 올라오지 않게 — 통합 모델 설계 §7-7·§7-9). 질의 이미지가 사진(7항)이면 견주지
     않는다. 등록 로고를 그대로 쓰고 이름만 다르게 넣어도 그 등록상표가 목록에 남고(견고성 점검 R-P0-1), 이름을 더한 질의의 전체
     등급은 같은 이미지만 넣은 질의보다 낮지 않다(사진 질의 제외). 표시 없는 v1.4.1 JSON 으로 돌리면 예전 동작이다.
7. **사진 질의**(v1.4): 질의 이미지가 사진(실물·간판·장면)으로 판정되면(`src.photo_mark` — CLIP 임베딩의 사진·그래픽 방향,
   학습 특징의 사진 판정과 같음) caveat `PHOTO_QUERY`. 이름 있는 판단은 이미지 축을 관측 없음으로 계산한다(학습에서 사진 쌍의
   이미지를 뺀 것과 같게 — `axes.x2_img` null). 이름 없는 판단은 계산을 바꾸지 않는다(이미지밖에 없으므로). 판정은 질의 쪽만
   한다(DB 등록 상표 1,469건 중 사진 판정 28건 = 1.9% — 2026-11-26 대표 표장 승격 전 1,383건 세대는 24건 1.7%, X2 설계 §7.6).
8. **업종 하한**(v1.4, 2026-11-20, `goods_floor`): 이름 없는 이미지+상품 판단(`noname:x2_whole+x4` — 이름 없는 질의, 이름 있는 질의의
   상표명 없는 후보, 6항의 이름을 뺀 판단)은 후보의 상품 겹침 `x4` 가 결합 하한(`coupling.floors.x4` = 0.0252, v1.3 JSON 그대로)
   이상이면 상품을 가린 이미지만 판단(`noname:x2_whole`)으로도 채점해 등급이 높은 쪽을 쓴다(같으면 이미지+상품 쪽). 겹침이 하한
   아래면 그대로 둔다 — 업종이 다르면 등급이 내려가도 된다. 이유: 이름 없는 하한을 방식마다 실제 검색에서 맞춰 이미지+상품의 위험
   하한(0.7892)이 이미지만(0.5724)보다 높아, 같은 로고에 업종이 조금 겹치는 업종 세트를 더하면 위험도는 오르는데(결합 제약) 등급은
   위험 → 검토 권장으로 내려갔다(설계 §7-4-4). v1.4.5 는 두 집합의 하한이 같지만 곱하기 항 때문에 이미지가 덜 닮은 쪽에서는 업종이
   조금 겹쳐도 이미지+상품 위험도가 이미지만보다 낮을 수 있어(예: 도형계 이미지 0.9·겹침 0.0252 → 검토 권장 0.550, 이미지만 위험
   0.575) 하한이 그대로 필요하다. 겹침이 하한 아래면 이미지+상품 판단은 이미지만 판단보다 높지 않다(겹침 0 은 `goods_rule` 로 보장,
   0–0.0252 는 채택 때 격자·실제 후보로 확인 — 설계 §7-12; v1.4.6 부터는 9항의 업종 상한이 등급으로도 보장). 이미지만 쪽이 쓰이면
   `rule_triggers` 에 `goods_floor`.
9. **업종 상한**(v1.4.6, 2026-11-24, `goods_cap`): 계수 JSON 의 `goods_cap.enabled` 가 참이면 업종이 다를 때(후보의 상품 겹침
   `x4` < 결합 하한 0.0252) 업종 판단의 등급을 업종 없는 짝 판단의 등급 이하로 내린다 — 이름 없는 이미지+상품(`noname:x2_whole+x4`)
   ↔ 이미지만(`noname:x2_whole`), 이름+상품(`x4`) ↔ 이름만(`base`), 이름+이미지+상품(`x2_whole+x4`) ↔ 이름+이미지(`x2_whole`).
   짝 판단의 등급은 단독 축·도형 규칙 등 그 판단에 걸리는 규칙까지 반영한 등급이고, 상한은 내리기만 한다 — 업종 판단이 짝
   판단보다 높을 때만 짝 판단을 쓰고 `rule_triggers` 에 `goods_cap`(`prob`·기여도·`pattern`·정렬 위치는 짝 판단의 것). 8항(업종이
   겹치면 이미지만 판단 이상)·결합 제약(이름 있는 쪽은 겹침이 하한 이상이면 업종 없는 판단 이상)과 함께 "업종이 겹치면 업종 없는
   판단의 등급 이상, 다르면 그 이하"가 등급에서 지켜진다. 6항(이미지만 판단과 견주기)은 상한 뒤에 걸린다. 이유: 이름 있는 업종
   집합은 v1.3 의 더하기 구조라 업종이 달라도 짝 판단보다 높은 후보가 있었다(통합 모델 설계 §7-13 — 대조군 확인용·표본 A 후보
   1,502). 계수·기준은 v1.4.5 그대로다.
10. **유명 상표 바닥**(v1.4.7, 2026-11-26, `famous_check`): 계수 JSON 의 `famous_check.enabled` 가 참이면 엔진이 질의마다 검색과
   별개로 유명 상표를 확인하고(§2-6), 그 판정이 준 바닥(위험 또는 검토 권장)이 위 1–9항으로 정한 전체 등급보다 높으면 **전체
   등급만** 그 바닥으로 올린다(`overall.famous_floor` true). `overall.prob`·`overall.pattern`·후보 목록·후보 등급·정렬·`caveats` 는
   그대로다 — 후보 배열은 같은 질의의 v1.4.6 응답과 같다(새 선택 필드 `famous_brand` 만 더해짐). 바닥은 내리지 않는다(전체 등급이
   이미 바닥 이상이면 그대로, `famous_floor` false). 후보가 없어 전체 등급이 null 인 질의도 바닥이 있으면 그 등급이 된다.
   유명 상표 확인이 꺼진 계수 JSON(≤ v1.4.6)으로 띄우면 이 항은 없고 응답에 `famous`·`famous_floor`·`famous_brand` 키도 없다.

### 2-6. `famous` — 유명 상표 확인 단계(v1.4.7, 선택 필드)

널리 알려진 상표의 보호는 일반 유사 판단(후보마다의 위험도)과 근거가 달라, 검색과 **별개로** 질의마다 확인해 맨 위 안내와 전체 등급의
바닥으로만 반영한다. 판정 규칙은 확정된 것(`ml/src/famous_check.py` + 등록부 `shared/famous_registry.json` — 확정 파일
`shared/famous_check_confirmed.json` 이 둘의 해시와 기준을 담는다, 통합 모델 설계 §7-14-12)이고 연결은 §7-14-13 이다.

| 필드 | 형식 | null | 뜻 |
|---|---|---|---|
| `status` | `"checked"` \| `"unavailable"` | 아니오 | 확인함 / 확인하지 못함(확인 중 예외 — 검색 결과는 그대로 나가고 `matches` 는 빈 배열, 원인은 서버 로그에만) |
| `brand_count` | int | 아니오 | 등록부의 브랜드 수(현재 58) — 이 목록에 있는 상표만 확인한다(화면 각주의 N) |
| `matches[]` | array | 아니오(빈 배열 가능) | 일치한 브랜드 — **브랜드마다 가장 강한 일치 하나, 강한 것부터 최대 2개**. 순서: 종류(강함 > 약함 > 설명적 사용) → 이름·이미지 속 글자가 로고보다 먼저 → 판정 모듈의 순서(같음 > 품음 > 소리 > 철자, 점수) |
| `matches[].brand` | string | 아니오 | 브랜드 이름(등록부) |
| `matches[].level` | `"강함"` \| `"약함"` \| `"설명적 사용"` | 아니오 | 종류. 강함 = 같거나 거의 같음(같음·설명 낱말을 붙인 꼴·소리 0.98·철자 0.90 이상, 로고), 약함 = 닮음(확정된 약한 일치 조건 W2), 설명적 사용 = 약한 표기(흔한 말·그 업종에서 식별력 없는 말)를 다른 말과 함께 쓰거나 업종이 다른 경우 등 — 바닥 없음 |
| `matches[].basis` | `"이름"` \| `"로고"` \| `"이미지 속 글자"` | 아니오 | 경로. 이름 = 질의의 `name`, 이미지 속 글자 = `name` 이 없는 이미지 질의에서 검색이 읽은 글자(`query_type.suggested_name` — 같음·설명 낱말을 붙인 꼴만, 강함만), 로고 = 질의 이미지와 그 브랜드의 대표 로고 |
| `matches[].notation` | string | 로고 일치면 null | 일치한 등록부 표기(예: `스타벅스`, `STARBUCKS`) |
| `matches[].matched_text` | string | 로고 일치면 null | 질의에서 맞은 글자(원래 대소문자·띄어쓰기 — 예: 질의 `파리 바게뜨` 의 `파리 바게뜨`, 질의 `텍사스 BBQ` 의 `BBQ`) |

| `matches[].floor` | `"위험"` \| `"검토 권장"` | 바닥이 없으면 null | 이 일치가 주는 전체 등급 바닥. 강함 = 위험(보호 범위가 같은·가까운 업종 중심이고 업종이 다르면 검토 권장), 약함 = 검토 권장(같은·가까운 업종 중심이고 업종이 다르면 없음), 설명적 사용 = 없음, 로고(강함) = 위험. 전체에 걸리는 바닥은 **모든** 일치(셋째 이후 포함)의 바닥 중 가장 높은 것 |
| `matches[].logos[]` | `{ "id": 출원번호, "image_url": string \| null }` | 아니오(빈 배열 가능) | 그 브랜드의 대표 로고 최대 2건 — "대표 로고(현재)" 먼저, 그다음 "과거 로고"; 로고 일치면 맞은 표장이 맨 앞. 지금 DB 에 있는 표장만 싣고 `image_url` 은 후보의 `image_url` 과 같은 꼴(같은 이미지 경로로 받는다) |

- **확인하는 것**: ① 이름 — `name` 을 판정 모듈에 그대로 넘긴다. ② 이미지 속 글자 — `name` 이 없고 검색이 이미지에서 읽은 글자가 있을 때
  (OCR 을 새로 돌리지 않는다). ③ 로고 — 질의 이미지가 있고 사진으로 판정되지 않았을 때, 그 이미지와 대표 로고의 유사도가 엔진의 "이미지만"
  판단에서 위험일 때만(유형은 2-4 6항의 `logo_floor` 가 쓰는 것과 같은 것 — 자동 유형이면 도형계, 유형을 문자로 고친 질의는 이미지만 판단이
  위험에 닿지 않아 로고 일치가 없다). 대표 로고와 질의 이미지가 **둘 다 글자 위주**(OCR 자동 유형이 문자)면 유사도 0.98 이상일 때만.
  사진으로 판정된 대표 로고도 보지 않는다. 대표 로고 가운데 지금 DB 색인에 없는 표장은 건너뛴다(기동 로그에 수만 남김).
- **업종**: 요청 형식은 그대로다 — 유사군 코드(`goods_codes`)만 받는다.
- **후보 목록과 무관**: 후보 배열·후보 등급·위험도·정렬은 유명 상표 확인이 없을 때(v1.4.6)와 같고, 달라지는 것은 이 필드들과
  바닥이 걸린 질의의 `overall.grade` 뿐이다(2-4 10항).
- **한계**: 등록부의 브랜드(현재 58개) 기준이다 — 목록에 없는 유명 상표는 일치가 없다고 나온다(화면 각주로 알린다, §4-6). 3호 사전의
  낱말을 붙인 꼴은 업종과 무관하게 강함이 될 수 있고(`네이버후드`), 소리가 같은 일반 낱말(`Neighbor` ↔ 네이버)도 강함이며, 상품을 하나씩
  고른 업종은 코드에서 정한 류가 실제보다 넓어 업종 겹침이 더 잡힐 수 있다(통합 모델 설계 §7-14-13 의 한계).
- `MARKLENS_FAKE_ML`(시험용 가짜 모델)에서는 로고 경로가 일치를 내지 않는다(가짜 임베딩은 유사도가 고정) — 이름 경로는 그대로 동작한다.

### 2-7. `name_words` — 질의 이름의 낱말별 식별력(선택 필드, 2026-11-26)

이름이 상품을 설명하거나 누구나 쓰는 말로만 되어 있으면 등록 자체가 어려울 수 있다는 것, 일부만 그런 말이면 그 낱말을 빼고 견줬다는 것을
알리는 안내(§4-7)에 쓴다. **새 판정이 아니다** — 엔진이 후보마다 요부를 정할 때 쓰는 식별력 판정(`Distinctiveness.judge_name` — 상품 접미어를 뗀 뒤의
낱말, [식별력 설계](MarkLens_식별력_설계.md) §2·§9)을 **질의의 이름과 질의의 업종(`goods_codes`)만으로** 부른 결과를 싣는다
(`ml/src/name_words.py`). 모델 버전은 그대로(v1.4.7)이고, 후보 배열·후보 등급·위험도·정렬·전체 등급은 이 필드가 없을 때와 같다.

|---|---|---|---|

| `5호 흔한 성` | 흔한 성·이름 |
| `6호 간단 표장` | 짧고 흔한 글자 |
| `다수 등록(A=…, N=…)` · `일반어(zipf …)` — 점수가 0.5 미만일 때 | 흔히 쓰는 말 |
| 그 밖의 코드(지금은 `빈 토큰` 뿐 — 이름에서 나온 낱말에는 붙지 않는다) | 그 밖 |

식별력 있는 낱말에만 붙는 코드(분류 없음): `유명 브랜드` · `조어` · `사람 검토 제외(…)` · `3호 기술적 표장(상품 미상|류 미지정):{종류}`
(점수를 0.5 로 누르기만 한다). 상품 접미어로 뗀 낱말은 따로 표시하지 않는다 — 떼어 낸 뒤의 낱말로 판정되어 그 업종의 고시 명칭이면 1호
(상품 이름), 아니면 다른 사유로 분류된다. 예: 카페 업종의 `커피` 는 `3호 기술적 표장:원재료(류 30,35,43)·1호 보통명칭` → 상품 이름
(엔진의 사유 나열은 3호가 앞이지만 분류는 1호가 먼저).

- **싣는 때**: `name` 이 있는 질의. 이름이 없는 질의(이미지만·지정상품만)에는 키가 없다. 정리 중 예외가 나도 검색은 그대로 나가고 이
  키만 빠진다(원인은 서버 로그에 예외 종류만 — 질의 이름을 새로 남기지 않는다).
- **질의의 업종 기준**: 1호(보통명칭)·3호(기술적 표장)는 상품에 상대적이다. 이 필드는 질의의 업종만으로 본 판정이고, 후보와 견줄 때
  엔진은 후보의 업종까지 합쳐 판정한다 — 쌍별 결과는 지금처럼 `candidates[].salient`(`query_tokens` = 그 쌍의 요부 후보, `removed` = 그
  쌍에서 뺀 낱말)에 있다. 업종을 고른 질의에서는 이 필드가 식별력 없다고 한 낱말이 어느 쌍에서도 요부 후보가 아니다(쌍의 업종이 질의의
  업종을 품는다). 반대로 식별력 있다고 한 낱말이 후보의 업종 때문에 **그 쌍에서만** 빠질 수는 있다.
- **업종이 없는 질의**: 식별력 판정은 업종을 모르면 "어느 업종의 상품 이름"(`1호 보통명칭(전역)`)도 약하다고 보지만, 엔진은 쌍마다
  후보의 업종으로 판정해 그 업종과 무관한 후보에는 그 낱말을 요부로 쓴다(`나무`·`다리`·`국수` 같은 낱말). 그래서 그 판정이 식별력 없다고
  한 낱말이라도 **어느 후보와 견줄 때 요부 후보로 쓰였으면**(풀 전체의 `salient.query_tokens`) 그 쌍의 판정으로 바꿔 `distinctive` true 로
  싣는다 — 응답이 "식별력 없는 말"이라고 한 낱말을 엔진이 요부로 쓴 일이 없게. 업종과 무관한 사유(지명·흔한 성·짧은 글자·절대적 기술
  표장·통계로 약한 낱말)는 그대로 실린다.
- **"빼고 견줬다"의 예외**: 식별력 없는 낱말이라도 ① 요부가 하나도 없는 이름이면 빼지 않고 전체로 견주고(`generic` `all`), ② 결합
  규칙(두 이름에 붙어 있는 약한 낱말 묶음·붙여 쓴 결합어, 식별력 설계 §2)이 요부로 되돌린 쌍에서는 빼지 않는다. 또 요부가 없는 이름의
  낱말이라도 후보 쪽의 약한 낱말과 같으면 그 쌍에서는 양쪽에서 함께 빠진다(`removed` 의 `side` `both` — §3-4 의 후보 2). 쌍마다의 사실은
  `salient` 가 정본이고, 화면은 "빼고 비교했어요"·"이름 전체를 견준 결과"를 보이는 후보 모두에서 사실일 때만 그린다(§4-7).
- **한계**: 회사 형태·부가어·영문 기능어(`주식회사`·`코리아`·`the` 등)는 축 함수가 판정 전에 버려 낱말 목록에 없고, 한자·기호만의
  낱말도 없다. 영문은 소문자로 실린다. 1호 판정은 유사군 코드가 걸친 **류 단위**라 넓다(카페 세트에서 `나무` 가 상품 이름). 35류(판매업)가
  든 업종에서는 3호 사전의 낱말이 업종과 상관없이 설명하는 말이 된다(의류 세트에서 `커피`). 영문 고시 명칭은 대조하지 않아 `coffee` 는
  상품 이름이 아니라 성질·품질(3호)로 나온다.

### 2-8. `cross_goods`·`cross_goods_more` — 업종은 다르지만 표장이 닮은 후보(선택 필드, 2026-11-26)

업종(`goods_codes`)을 넣은 질의에서 업종은 다르지만 표장이 닮은 후보를 화면이 알아볼 수 있게 한다(§4-8). **새 판정이 아니고 등급 계산에도
쓰지 않는다** — 엔진이 후보를 채점하는 같은 함수를 업종 축만 빼고 한 번 더 부른 등급을 싣는다([통합 모델 설계](MarkLens_통합모델_설계.md)
§7-15). 모델 버전은 그대로(v1.4.7)이고, 후보 배열·후보 등급·위험도·정렬·전체 등급은 이 필드들이 없을 때와 같다.

**정의** — "업종은 다르지만 표장이 닮은 후보": 업종을 넣은 질의에서 ① 후보와의 업종 겹침(`axes.x4`)이 결합 하한 0.0252(통합 모델의
`coupling.floors.x4` — 업종 하한·상한이 쓰는 것과 같은 기준, §2-4 8·9항) 미만이고 ② 업종 없이 본 등급이 검토 권장 이상인 후보.

`candidates[].cross_goods`(업종을 넣은 질의의 모든 후보 — `cross_goods_more.candidates[]` 의 후보도):

| 필드 | 형식 | null | 뜻 |
|---|---|---|---|
| `differs` | bool | 후보의 유사군 정보가 없어 업종 겹침을 모르면 null(`axes.x4` 가 null 일 때) | 업종이 다른가 = `axes.x4` < 0.0252. 모르는 것은 "다름"이 아니다 — 표시하지 않는다 |
| `grade_without_goods` | 4등급 | `differs` 가 true 가 아니면 null | 업종 없이 본 등급 — 이 후보의 판단에서 업종 축만 뺀 등급(아래) |
| `flagged` | bool | 아니오 | 위 정의에 맞는가 = `differs` 가 true 이고 `grade_without_goods` 가 검토 권장 이상 |

- **업종 없이 본 등급**: 후보를 채점하는 같은 함수를, 업종 겹침만 관측 없음으로 두고 다시 부른 등급이다. 이름 있는 판단이면 업종 상한
  (`goods_cap`, §2-4 9항)이 견주는 짝 판단(`x4` → `base`, `x2_whole+x4` → `x2_whole`), 이름 없는 판단이면 이미지만 판단이고, 엔진이 후보의
  등급을 정할 때와 같은 순서로 이미지만 판단과의 비교(`nameless_floor` — §2-4 6항)까지 거친다. 단독 축 규칙·도형 규칙이 반영된 등급이다.
  축 점수와 요부는 그대로 둔다(업종을 넣고 계산한 식별력 맥락 그대로라, 업종 없이 다시 검색한 결과와는 다를 수 있다).
- 업종 상한 때문에 업종이 다른 후보의 `risk.grade` 는 `grade_without_goods` 보다 높지 않다 — 그래서 **업종이 다른데 검토 권장·위험으로
  보이는 후보는 모두 `flagged` 다.** 반대로 `flagged` 인데 `risk.grade` 가 주의·안전일 수는 있다(업종이 달라 내려간 것).
- 견줄 표장 축이 하나도 없는 판단(이름도 이미지도 견주지 못하고 업종만으로 본 판단 — `risk.pattern` `x4` 에 이름 축이 모두 null)은 업종
  없이 보면 근거가 없어 `안전` 이고 표시되지 않는다.
- **싣는 때**: `goods_codes` 가 있는 질의. 없는 질의에는 후보에도 최상위에도 키가 없다. 계산 중 예외가 나면 그 후보의 키만 빠지고 검색은
  그대로 나간다(원인은 서버 로그에 예외 종류만).

`cross_goods_more`(최상위 — 업종을 넣은 질의만):

| 필드 | 형식 | null | 뜻 |
|---|---|---|---|
| `count` | int | 아니오 | 처음 보이는 범위(응답의 `candidates[]` — `top_k`) 밖의 후보 풀에서 정의에 맞는 후보 수 |
| `candidates[]` | array | 아니오(빈 배열 가능) | 그 가운데 **최대 5개** — `candidates[]` 와 같은 꼴(`cross_goods`, 해당하면 `famous_brand` 포함). 업종 없이 본 등급이 높은 것부터, 같은 등급이면 유명 상표 등록부의 표장(`famous_brand` 가 붙는 후보) 먼저, 그다음 풀의 정렬 순서 |

- 후보 풀(§1-3 — 축별 상위를 모은 것, `meta.pool.total`) 안에서 센 것이다. DB 전체를 다시 찾은 것이 아니다.
- `top_k` 를 늘리면 그만큼 `candidates[]` 로 옮겨 가고 `count` 가 준다. `candidates[]` 와 겹치는 후보는 없다.

## 3. 예시 JSON

네 예시 모두 2026-11-26 의 코드·데이터로 **실제 엔진**(실제 CLIP·OCR·관념 모델, DB 1,469건, 통합 모델 v1.4.7)이 낸 응답 그대로다 — 같은 날 설명적 이름 안내를 더했을 때의 예시와 새 선택 필드(업종을 넣은 §3-1·§3-3·§3-4 의 후보마다 `cross_goods`, 최상위 `cross_goods_more` — §3-2 는 업종이 없어 없다, §2-8)·`elapsed_ms` 말고 같다(후보는 같다). 그 전의 경과 — 앞의 세 예시는 같은 날 유명 상표 확인을 연결했을 때의 예시와 새 선택 필드 `name_words`(이름이 있는 §3-1·§3-3 에만 — §3-2 는 이름이 없어 없다)·`elapsed_ms` 말고 같고(후보는 같다), 넷째 예시(§3-4)는 모든 낱말이 상품을 설명하는 말인 이름이다. 그 전의 경과 — 앞의 두 예시는 2026-11-24 의 v1.4.6 예시(DB 1,383건)와 `model_version`·`dataset_info`(`총_상표수`·`생성일자`)·`index_size`·`elapsed_ms`, 그리고 새 선택 필드 `famous`(확인함·일치 없음)·`overall.famous_floor`(false)만 다르고 후보는 같다. 셋째 예시(§3-3)는 유명 상표 일치가 든 응답이다
(`engine.multi_search`, 첫 호출 준비를 한 번 한 뒤의 호출 — `elapsed_ms` 는 그때 값; 그 전 예시들의 경과 — 2026-11-20 의 v1.4 예시와 다른 곳은 `model_version`·`thresholds.grade`
검토 권장·문자상표 예시 3·4위 등급(검토 권장 → 주의)·`elapsed_ms` 뿐 — 두 예시는 이름 + 이미지 질의가 아니라 v1.4.2 의 `logo_floor` 가 걸리지 않아, 같은 날 v1.4.1 예시와는 `model_version`·`elapsed_ms` 만 다르다; v1.4.3 의 `weak_run` 도 두 예시에서 결과를 바꾸지 않아 v1.4.2 예시와 `model_version`·`elapsed_ms` 만 다르다; v1.4.5 의 곱하기 항은 두 예시에 이름 없는 이미지+업종 판단이 없어 후보를 바꾸지 않아, v1.4.3 예시와 `model_version`·`meta.thresholds.nameless` 의 이미지+업종 하한·`elapsed_ms` 만 다르다; v1.4.6 의 업종 상한도 두 예시의 결과를 바꾸지 않아 — 문자상표 예시의 BLU hands 는 업종 겹침 0 이지만 짝 판단(이름만)도 단독 규칙으로 검토 권장이라 그대로 — v1.4.5 예시와 `model_version`·`elapsed_ms` 만 다르다). `image_url` 만(대표 로고의 것도) 브라우저 측 값(`/api/images/…`)으로
바꿨다. 프론트는 이 네 응답을 Vitest 픽스처(`frontend/test/fixtures/search-v2-{text,image,famous,descriptive}.json`, 블록과 바이트 단위로 같음)로,
백엔드는 스키마·키 집합 시험에 그대로 쓴다.

### 3-1. 문자상표 — 이름 "블루커피" + 카페 세트, 이미지 없음

요청(BFF): `POST /api/search/v2?top_k=4`, `X-Turnstile-Token`, multipart
`name=블루커피`, `goods_codes=G0301`, `goods_codes=G0502`, `goods_codes=S120602`, `goods_codes=S2005`
(업종 세트 "카페" = 커피전문점업 43류·커피 30류·커피 소매업 35류의 유사군 합집합).

판정 흐름: 입력 토큰 `블루`는 요부 후보로 남고 `커피`(3호 기술적 표장 원재료·1호 보통명칭)는 제외된다. 이미지가 없고 상품이 있어
이름 있는 계수 집합 `x4`(절편 -3.4535 → `missing_adjustment` 0.018)를 쓴다. 1·2위 BLU hands(같은 출원인의 두 등록)는 후보 쪽 `hands`
(일반어·다수 등록)가 빠져 `블루` ↔ `blu` 로 비교되고 호칭 1.0·관념 0.9186 이라 단독 규칙(`standalone_x1`·`standalone_x3`)이 걸린다 —
위험도 0.524(검토 권장 하한 0.5059 이상, 정밀도 0.8 목표 미달 대체값인 위험 하한 0.5902 아래)라 "검토 권장". 3·4위는 지정상품이 겹치는
(자카드 0.6·0.75) 커피 관련 상표로 위험도 0.378·0.339 — 검토 권장 하한 0.5059 아래라 "주의"(v1.4 의 하한 0.1805 에서는 검토 권장이었다). 유사군 보유가 전건(1,469/1,469)이라 `GOODS_COVERAGE` 는 나오지 않는다(§2-5). **업종은 다르지만 표장이 닮은 후보**(§2-8): 1·2위 BLU hands 는 카페 세트와 업종 겹침이 0 이고(`cross_goods.differs` true) 업종 없이 봐도 검토 권장이라 `flagged` — 화면은 그 카드에 "업종 다름"을 붙이고, 가장 위 후보가 그런 후보라 전체 등급 옆에 "가장 닮은 상표가 다른 업종에 있어요. …" 한 줄을 보인다(§4-8). 3·4위는 업종이 겹쳐 `differs` false. 처음 보이는 범위 밖에는 그런 후보가 없다(`cross_goods_more.count` 0).

### 3-3. 유명 상표 일치 — 이름 "스타벅스" + 의류 세트, 이미지 없음

요청(BFF): `POST /api/search/v2?top_k=3`, multipart `name=스타벅스`, `goods_codes=` 의류 세트(업종 세트 "옷가게·온라인 의류 쇼핑몰" —
25류 의류와 35류 의류 소매업의 유사군 11개).

판정 흐름: 후보는 발음·철자·유사군 풀에서 58건이 모였고 앞 3건은 STARBUCKS 상표다 — 호칭이 같아(`x1` 1.0) 단독 규칙으로 검토 권장
(위험도 0.542·0.537·0.524, 이름+상품 계수 집합 `x4`)이고 업종이 달라 위험에는 닿지 않는다. **유명 상표 확인**(§2-6): 이름이 등록부의
표기 `스타벅스` 와 같아 강함(경로 이름), 보호 범위가 업종 불문이라 업종이 달라도(`goods_overlap` false — 판매업 35류는 빼고 본다)
바닥이 위험 → **전체 등급만** 위험으로 오른다(`overall.famous_floor` true). `overall.prob` 0.542 와 후보 배열은 같은 질의의 v1.4.6
응답과 같고, 후보 셋은 등록부의 표장이라 `famous_brand` 가 붙는다. 화면은 맨 위에 배너("널리 알려진 상표 '스타벅스'와 이름이 같거나
거의 같아요")와 대표 로고 2장을 보이고, 전체 등급에는 "널리 알려진 상표와 같거나 거의 같아서 이 등급으로 봤어요."를 보이며 위험도 %·
등급 눈금·정밀도 문구는 그리지 않는다(§4-6). **업종은 다르지만 표장이 닮은 후보**(§2-8): 1·2위는 의류 세트와 업종이 조금 겹쳐(겹침 0.077·0.056 ≥ 0.0252) `differs` false, 3위 STARBUCKS COFFEE 는 겹침 0 이고 업종 없이 본 등급이 검토 권장이라 `flagged` — 유명 상표 표시가 붙은 후보라 카드의 설명은 "업종은 다르지만 널리 알려진 상표라 문제가 될 수 있어요."다. 처음 보이는 범위(앞 3) 밖에도 그런 후보가 7건 있어 `cross_goods_more` 에 5건이 실리고, 화면은 목록 아래 접힌 칸 "업종은 다르지만 표장이 닮은 상표 7건"으로 보인다. 전체 등급은 유명 상표 바닥이 정했으므로 전체 등급 옆의 한 줄은 없다(§4-8).

### 3-4. 설명적 이름 — 이름 "맛있는 커피 전문점" + 카페 세트, 이미지 없음

요청(BFF): `POST /api/search/v2?top_k=3`, multipart `name=맛있는 커피 전문점`, `goods_codes=G0301,G0502,S120602,S2005`(업종 세트 "카페").

판정 흐름: **낱말별 식별력**(§2-7) — 이름의 세 낱말이 카페 업종에서 모두 식별력 없는 말이다(`name_words.generic` `all`): `맛있는` 은
3호 품질 표시(성질·품질), `커피` 는 그 업종의 고시 명칭이자 3호 원재료 표시(상품 이름 — 사유가 여럿이면 1호가 먼저), `전문점` 은 3호
용도 표시(성질·품질). 요부가 없는 이름이라 엔진은 질의의 낱말을 빼지 않고 견준다(후보 1·3의 `salient.query_tokens` 가 비어 있고
`removed` 에 질의 쪽 낱말이 없다). 다만 후보 2 `맛있는 건강 본죽` 은 자기 요부(`건강`·`본죽`)가 있어 그쪽의 약한 낱말 `맛있는` 이 빠지는데,
그 낱말이 질의에도 있어 **이 쌍에서는 양쪽에서 함께 빠진다**(`removed` 의 `side` `both`). 후보는 발음·철자·관념·유사군 풀에서 55건이

## 4. 화면 문구 규약(프론트가 그대로 구현)

### 4-1. 근거 축(`risk.contributions`)

- 표시 순서: 기여도 **내림차순**. 0 이하인 축은 목록에서 빼고(음수는 "위험을 낮춘 요소"로 접힘 영역에만), null 축(`axes.*` 가 null)은
  "정보 없음"으로 회색 처리해 맨 뒤.
- 라벨: `X1` → 호칭(발음), `X2` → 외관(철자·이미지), `X3` → 관념(뜻), `X4` → 지정상품, `요부` → 요부(식별력).
- 바 길이 = 해당 축 기여도 ÷ 양수 기여도 합(예 3-1 후보 1: X1 3.628/4.688 = 77%, X2 13%, X4 8%, X3 2%).
- 축 값 표기는 `axes.*` 를 백분율 정수로("호칭 89%") — **내림**(0.7499 → 74%: 시각 상태 0.75·도형 규칙 0.9·단독 임계값 같은
  기준을 넘지 않은 값이 넘은 것처럼 보이지 않게, 위험도 %·지정상품 겹침 %도 같다, 2026-11-21), 바는 기여도로 — 둘을 섞지 않는다(점수가 높아도 계수가 작으면 기여도가 작다: X3).
- `rule_triggers` 가 있으면 등급 옆에 한 줄(2026-11-26 문구 — 카드의 최종 등급이 무엇이든 참인 문장만: 하한 규칙은 "… 이상으로 봤어요",
  상한 규칙은 "… 더 높이지 않았어요", 특정 등급으로 올렸다·내렸다고 단정하지 않는다): `standalone_x1` "발음이 거의 같아서 검토 권장
  이상으로 봤어요", `standalone_x2_text` "철자가 매우 비슷해서 검토 권장 이상으로 봤어요", `standalone_x3` "뜻이 매우 비슷해서 검토 권장
  이상으로 봤어요", `figure_x2_img` "도형이 매우 비슷해서 검토 권장 이상으로 봤어요. 도형 비교는 검증 데이터가 적어 참고용이에요",
  `nameless_floor` "로고만 봤을 때의 등급이 더 높아서 그 등급 이상으로 봤어요", `goods_floor` "업종이 겹쳐서 로고만 봤을 때의 등급
  이상으로 봤어요", `goods_floor_named` "업종이 겹쳐서 업종 없이 봤을 때의 등급 이상으로 봤어요", `goods_cap` "업종이 달라서 등급을 더
  높이지 않았어요"(같은 카드에 "업종 다름" 표시가 있으면 숨긴다 — §4-8), 문구가 없는 코드는 "따로 정한 규칙이 적용됐어요". 등급을 말하는
  문장은 카드의 등급이 그보다 낮으면 보이지 않는다. `nameless_floor` 는 v1.4.2(`logo_floor`, §2-4 6항)부터
  유형을 고치지 않은 이름 + 이미지 질의에도 붙어(등록 로고를 그대로 쓰고 이름만 다른 입력 — 견고성 점검 R-P0-1) 두 경우에 맞는 문구로 바꿨다(2026-11-23,
  `ResultViewV2.tsx` — 그 전 문구 "도형으로 고친 질의라 로고만으로 본 판단의 등급을 썼습니다").

### 4-2. 요부·제외 토큰(`salient`)

생성 규칙 — 후보 카드마다 `removed` 가 비어 있지 않으면 한 문장:

```
'{removed 토큰들을 ·로}'은(는) {사유 표현}이라 제외, '{query_tokens 를 ·로}'(으)로 비교
```

예 3-1 후보 1: **'커피'는 흔한 말이라 제외, '블루'로 비교** (후보 쪽 제외 토큰 `blue`·`cafe` 는 같은 틀로 두 번째 문장:
"'blue·cafe'는 흔한 말이라 제외, '블루카페'로 비교"). `side: both` 는 한 문장으로 합친다. 조사(은/는, 으로/로)는 마지막 글자의 받침으로
고른다(라틴 문자 토큰은 "는"·"로").

사유 → 표현(첫 사유 기준, 여러 개면 가장 앞의 것):

| `reason` 접두 | 표현 |
|---|---|
| `1호 보통명칭` | 흔한 말(상품 이름) → 짧은 문장에서는 **흔한 말** |
| `3호 기술적 표장` | 상품을 설명하는 말 |
| `4호 지명` | 지명 |
| `5호 흔한 성` | 흔한 성씨 |
| `6호 간단 표장` | 간단한 표장 |
| `일반어` / `다수 등록` | 흔한 말 / 여러 상표에 흔히 쓰이는 말 |

전체 `reason` 문자열은 툴팁(또는 "자세히")에 그대로 보여 준다. `query_tokens` 가 비어 있고 이름이 있으면 "식별력 있는 부분이 없어 전체로
비교했어요"(2000후2453).

### 4-3. 등급 정밀도(`meta.grade_precision`)

- 문구: **"검증 데이터 기준 10건 중 {round(grade_precision × 10)}건"** → 0.69 → "검증 데이터 기준 10건 중 7건". 전체 문장:
  "'위험'으로 나온 상표 쌍은 검증 데이터 기준 10건 중 7건이 심결에서 유사로 판단됐어요". 유명 상표 확인이 전체 등급을 올린 경우
  (`overall.famous_floor` true)에는 전체 등급 칸에서 이 문장을 보이지 않는다(모델이 낸 '위험'에만 맞는 말).
- 표시 위치: `overall.grade` 또는 후보 `risk.grade` 가 **"위험"** 이고 **이름 있는 판단**(`pattern` 이 `noname:` 이 아님)일 때 등급 배지
  옆 한 줄. 다른 등급·이름 없는 판단에는 쓰지 않는다(정밀도 값이 이름 있는 판단의 위험 등급 것이므로).
- 값은 응답에서 읽는다(상수 금지). 모델이 재학습되면 숫자가 바뀐다.

### 4-4. 등급 표기

| 등급 | 색(제안) | 한 줄 설명 |
|---|---|---|
| 안전 | 회색 | 비교한 상표 가운데 가까운 것을 찾지 못했어요. 안전하다는 뜻은 아니에요 / 로고만 넣은 검색: 로고가 가까운 상표를 찾지 못했어요. 안전하다는 뜻은 아니에요 |
| 주의 | 노랑 | 조금 닮은 상표가 있어요 / 로고만: 로고가 조금 닮은 상표가 있어요 |
| 검토 권장 | 주황 | 닮은 선행 상표가 있을 수 있어요. 전문가 검토를 권해요 / 로고만: 로고가 닮은 선행 상표가 있을 수 있어요. 전문가 검토를 권해요 |
| 위험 | 빨강 | 많이 닮은 선행 상표가 있어요 / 로고만: 로고가 많이 닮은 선행 상표가 있어요 + §4-3 문구 |

"로고만 넣은 검색"은 이름이 없고 이미지가 있는 질의다(이름이 있으면 로고가 함께 있어도 앞쪽 문구). 축 수("여러 축"·"일부 축")는 말하지
않는다(2026-11-26).

`overall.grade` 가 null(후보 0건)이면 등급 배지 대신 `caveats` 의 "비교할 후보가 없습니다 — 안전하다는 뜻이 아닙니다"를 1층에 둔다.

이름 없는 판단(v1.4) — `risk.pattern`(전체는 `overall.pattern`)으로 판별하고 요청 상태(이름을 넣었는지)에 기대지 않는다:

- 이름 없는 판단은 **위험도 %를 보이지 않고** 등급과 이미지 유사도(`axes.x2_img`)를 보인다. 전체 등급이 이름 없는 판단에서 나왔으면
  전체 위험도 %(`overall.prob`)도 숨긴다. 이유: 이름 있는 입력과 이름 없는 입력의 % 눈금이 달라 섞어 보면 오해한다.
- 등급 눈금은 그 판단의 하한으로 그린다(§2-3). 이름 있는 판단만 위험도 위치 표식을 둔다. 하한은 숫자로 보이지 않고 구간 폭
  (정확한 값)으로만, 표식도 반올림 없는 위치로 그린다 — 하한이 % 정수 사이에 있으면(위험 0.5902) 같은 "59%"가 하한 아래(0.5900·0.5901,
  검토 권장)와 위(0.5902–0.5999, 위험)에 함께 나올 수 있고, 내림이라 하한 아래 값이 "60%"로 올라가 보이지는 않는다.
- 이름 없는 질의(`name` 없음)에는 1층에 한 줄: **"상표명·업종을 넣으면 더 정확하게 판단해요"**.

### 4-5. 도형 caveat·시각 상태

- `risk.figure_caveat` 가 true 인 카드와 `overall` 에 "로고 파일끼리 비교한 결과예요. 도형 유사는 검증 데이터가 적어 참고용이에요"
  배지(§2-5 `FIGURE_LOW_DATA` 와 같은 문장). 이미지 입력이면 `axes.x2_img` 를 "이미지 유사 93%"로 항상 표시하고, `visual_status`(있으면)를
  v1 과 같은 4상태 문구로 1층에 함께 둔다.
- 사진 질의는 `caveats` 의 `PHOTO_QUERY` 문구("사진으로 보여요 — 로고 파일을 올리면 외관 비교가 더 정확해요")를 그대로 보인다.
- `query_type` 은 1층에 "유형: 도형(이미지에서 판정)" 식으로 보여 주고 "유형 고치기" 버튼 → `type_override` 로 재요청(토큰 새로 발급).
  `source: fallback` 이면 caveat 의 `OCR_FALLBACK` 문구를 버튼 옆에 둔다.
- `query_type.suggested_name` 이 있으면(이름 없는 이미지 질의) 1층에 "이미지에서 '…'를 읽었어요" + **"상표명으로 넣기"**
  버튼 → 사용자가 확인·수정하면 `name` 을 채워 **재요청**(새 Turnstile 토큰). 자동으로 다시 검색하지 않는다.

### 4-6. 유명 상표 확인(`famous`, v1.4.7)

- **맨 위 안내 배너**: `famous.status` 가 `checked` 이고 `matches` 가 하나 이상이면 결과 맨 위에 배너 하나 — `matches[0]`(가장 강한
  일치)을 보여 주고 `matches[1]` 이 있으면 한 줄로 덧붙인다. `matches[0].logos` 의 대표 로고 그림(최대 2장, 대체 글
  `'{브랜드}' 대표 로고`)을 함께 보이되, 그림을 못 받으면 그림 없이 보인다. 배너에는 제목 요소를 두고, 종류는 색만으로 구분하지 않는다
  (아이콘 + "유명 상표 확인 · 강한 일치 / 약한 일치 / 설명적 사용"). 질의에서 온 글자는 텍스트로만 그린다.
- 문구는 `level`(종류)과 `basis`(경로)로 고른다(바닥이 없어도 약함은 약함 문구). 브랜드·표기·글자 바로 뒤의 조사만 받침에 맞춘다
  (`'스타벅스'와` / `'삼성'과`, `'토스'는` / `'당근'은`, `'…'가` / `'…'이` — 한글 음절이 아니면 받침 없는 것으로 본다).

| 경우 | 제목 | 본문 |
|---|---|---|
| 이름 강함, 바닥이 위험 | 널리 알려진 상표 '{브랜드}'와 이름이 같거나 거의 같아요 | 널리 알려진 상표는 업종이 달라도 보호될 수 있어요. 소비자가 관련 있는 곳으로 오해하거나 그 상표의 명성을 해친다고 보면, 등록이 거절되거나 쓰는 것 자체가 분쟁이 될 수 있어요. 다른 이름을 권해요. |
| 이름 강함, 바닥이 검토 권장(업종이 다른 경우) | 위와 같음 | 업종이 달라서 함께 등록될 수도 있지만, 유명한 상표라 문제가 될 수 있어요. 출원 전에 꼭 확인해 보세요. |
| 이름 약함(바닥이 있든 없든) | 널리 알려진 상표 '{브랜드}'와 이름이 닮았어요 | 유명한 상표를 떠올리게 하는 이름은 업종이 달라도 문제가 될 수 있어요. 출원 전에 꼭 확인해 보세요. |
| 설명적 사용 | '{표기}'는 널리 알려진 상표 이름이기도 해요 | 상품을 설명하는 말로 쓰는 건 괜찮을 수 있어요. 다만 가게 이름처럼 눈에 띄게 쓰거나 그 상표의 글자 모양·로고와 비슷하게 쓰면 문제가 될 수 있어요. |
| 로고 강함 | 널리 알려진 상표 '{브랜드}' 쪽의 등록 로고와 같거나 거의 같아요 | 첫 줄의 본문에서 끝 문장만 "다른 로고를 권해요." |
| 이미지 속 글자 강함 | 이미지 속 글자 '{글자}'가 널리 알려진 상표 '{브랜드}'와 같거나 거의 같아요 | 바닥이 위험이면 첫 줄, 검토 권장이면 둘째 줄의 본문 |

- 각주(모든 배너): **"MarkLens가 정리한 유명 상표 {N}개 브랜드 기준이에요. 목록에 없는 유명 상표도 있어요."** — N = `famous.brand_count`.
- 둘째 브랜드 한 줄: 강함 "널리 알려진 상표 '{브랜드}'와도 같거나 거의 같아요." · 약함 "널리 알려진 상표 '{브랜드}'와도 닮았어요." ·
  설명적 사용 "'{표기}'도 널리 알려진 상표 이름이에요."
- `famous.status` 가 `unavailable` 이면 배너 없이 한 줄: **"유명 상표 확인을 하지 못했어요."** `famous` 가 없거나 일치가 없으면 아무것도
  그리지 않는다.
- **전체 등급**: `overall.famous_floor` 가 true 면 그 까닭을 한 줄로 — 바닥을 준 일치(`floor` 가 `overall.grade` 와 같은 첫 일치)가
  약함이면 "널리 알려진 상표와 이름이 닮아서 이 등급으로 봤어요.", 그 밖에는 "널리 알려진 상표와 같거나 거의 같아서 이 등급으로 봤어요."
  이때 전체 위험도 %·등급 눈금·등급 설명 문구·정밀도 문구(§4-3)는 그리지 않는다(위험도에서 나온 설명이 그 등급의 근거처럼 보이지 않게 —
  후보 카드의 등급·근거는 그대로). false 거나 없으면 예전과 똑같이 그린다.
- **후보 카드**: `famous_brand` 가 있으면 "유명 상표 · {브랜드}" 표시.

### 4-7. 설명적 이름 안내(`name_words`, 2026-11-26)

문구는 `frontend/lib/descriptiveNotice.ts` 한 곳에 모은다. 이름·낱말 바로 뒤의 조사만 받침에 맞춘다(`'커피'는` / `'전문점'은` — 한글
음절이 아니면 받침 없는 것으로 본다). 질의에서 온 글자는 텍스트로만 그린다. `name_words` 가 없거나 `generic` 이 `none` 이면 아무것도
그리지 않는다.

- **맨 위 안내의 순서**: ① 유명 상표 배너(강함·약함, §4-6) ② 설명적 이름 안내 ③ 유명 상표의 "설명적 사용" 안내(§4-6 의 같은 배너 —
  종류가 설명적 사용이면 설명적 이름 안내 뒤로 간다). 유명 상표 확인을 하지 못했다는 한 줄은 맨 위 그대로다.
- **유명 상표 배너가 이름 쪽의 강한 일치로 뜨면 그리지 않는다** — 배너가 그리는 일치(`famous.matches` 의 첫째와 둘째 줄) 가운데 `level` 이
  `강함` 이고 `basis` 가 `로고` 가 아닌 것(`이름`·`이미지 속 글자`)이 있으면, 설명적 이름 안내를 **(가)(나)(다)와 (라) 한 줄까지 모두**
  그리지 않는다. 이름이 널리 알려진 상표와 같거나 거의 같다고 알리는 자리에서 그 이름을 "누구나 쓰는 말"이라고 함께 말하지 않는다
  (`파리바게트` + 빵집 — 엔진이 `파리`·`바게트` 로 나눠 `generic` 이 `all` 이지만 배너만 보인다; `김가네` + 분식도 같다). 약한 일치의
  배너, 로고로만 강하게 일치한 배너(`basis` `로고`), 설명적 사용 안내에서는 아래 규칙 그대로다. 응답의 `name_words` 는 그대로 실린다 —
  화면이 그리지 않을 뿐이다.
- **(가) 큰 안내** — `generic` 이 `all` 이고, 식별력 없는 낱말 가운데 **"흔히 쓰는 말"이 아닌 분류(상품 이름·성질·품질·지역 이름·흔한
  성·이름·짧고 흔한 글자)의 낱말이 하나 이상** 있고, 유명 상표 배너(강함·약함)가 없을 때. 모든 낱말이 "흔히 쓰는 말"(통계로 약해진
  낱말)뿐이면 큰 안내 대신 (다)로 보인다 — "그 밖"도 큰 안내를 띄우지 않는다.

| 자리 | 문구 |
|---|---|
| 제목 | 이 이름은 상표로 등록받기 어려울 수 있어요 |
| 본문 | '{이름}'은(는) 모두 상품을 설명하거나 누구나 쓰는 말이에요. — {이름}은 사용자가 넣은 이름 그대로 |
| 낱말 목록 | {낱말} — {분류 문구} (식별력 없는 낱말마다 한 줄, `more_generic` 이 있으면 끝에 "외 N개") |
| 이어서 | 이런 말은 다른 가게도 자기 상품을 설명하려면 써야 해서, 한 사람만 쓰도록 등록받기 어려워요. 등록이 안 되면 다른 가게가 같은 이름을 써도 막을 수 없어요. |
| 이렇게 해 보세요 | · 직접 지은 말을 이름의 중심에 넣어 보세요. (분류가 상품 이름인 낱말이 있으면 이어서 "예: '○○ {그 낱말}'처럼요." — 여럿이면 앞의 것) · 설명하는 말은 같이 써도 괜찮아요. 다만 그 말 자체는 혼자 쓸 수 없어요. |
| 버튼 | 다른 이름으로 다시 확인하기 — 입력(이미지·이름·지정상품)을 그대로 둔 채 입력 화면으로 돌아가 이름 칸을 고른다(전체 선택). 자동으로 다시 검색하지 않는다(유형 고치기·상표명으로 넣기와 같은 흐름, §4-5) |
| 작은 글씨 | 최종 판단은 특허청 심사에서 정해져요. 오래 써서 많은 사람이 알아보는 이름은 예외가 될 수 있어요. |

- **(나) 작은 안내** — `generic` 이 `some` 이고 **"빼고 비교했어요"가 보이는 후보 모두에서 사실일 때만** 한 줄: **'{낱말들}'은(는) 누구나
  쓰는 말이라 빼고 비교했어요.** + 펼치는 버튼 "왜요?". {낱말들}은 식별력 없는 낱말을 가운뎃점으로 이은 것(`'서울·커피'는`), 싣지 않은
  낱말에 식별력 없는 말이 있으면 `'…' 외 N개는`. 펼치면 낱말별 분류 문구와 "이런 말은 누구나 써야 해서 혼자 쓸 수 없어요." 한 문장.
  - 사실인지는 응답으로 화면이 판단한다((라)와 같은 방식): **이름을 견준 후보**(`title` 이 있는 후보)마다 실린 식별력 없는 낱말이 모두
    `salient.removed` 에 `side` `query`·`both` 로 들어 있고, 싣지 않은 식별력 없는 낱말 수(`more_generic`)만큼 질의 쪽에서 뺀 낱말이 더
    있어야 한다. 이름을 견준 후보가 하나도 없으면 견준 것이 없으므로 사실이 아니다.
  - 사실이 아니면 **이 안내를 그리지 않는다**(결합 규칙이 그 낱말을 요부로 되돌린 후보, 후보의 업종 때문에 그 쌍에서는 질의에 요부가
    없어 전체로 견준 후보가 보일 때 — §2-7). 후보 카드는 §4-2 의 문장으로 무엇을 뺐는지 그대로 말한다.
- **(다) 작은 안내** — `generic` 이 `all` 인데 유명 상표 배너(약한 일치, 또는 로고로만 강한 일치)가 있거나, 모든 낱말이 "흔히 쓰는
  말"뿐일 때 한 줄:
  **'{이름}'은(는) 모두 누구나 쓰는 말이에요.** + 펼치는 버튼 "자세히". 펼치면 (가)의 낱말 목록과 이어지는 설명.
- **분류 문구**(`words[].category` → 문구):

| 분류 | 문구 |
|---|---|
| 상품 이름 | 파는 상품이나 서비스의 이름 그 자체예요 |
| 성질·품질 | 맛·품질·재료·쓰임새 같은 성질을 설명하는 말이에요 |
| 흔히 쓰는 말 | 여러 상표에 흔히 쓰이는 말이에요 |
| 지역 이름 | 널리 알려진 지역 이름이에요 |
| 흔한 성·이름 | 흔한 성이나 흔히 쓰는 이름이에요 |
| 짧고 흔한 글자 | 너무 짧거나 흔한 글자·숫자예요 |
| 그 밖(모르는 값 포함) | 식별력이 약한 말이에요 |

- **(라) 전체 등급 옆의 한 줄** — `generic` 이 `all` 이고 **보이는 후보 가운데 질의의 낱말이 빠진 것이 하나도 없을 때만**
  (`candidates[].salient.removed` 에 `side` 가 `query`·`both` 인 항목이 없을 때): "설명하는 말로만 된 이름이라, 아래는 이름 전체를 견준
  결과예요." 엔진은 요부가 없는 이름의 낱말을 빼지 않지만, 후보 쪽의 약한 낱말이 질의에도 있으면 그 후보와 견줄 때는 양쪽에서 함께
  뺀다(§2-7) — 그런 후보가 보이면 이 줄은 사실이 아니어서 그리지 않는다(그 후보 카드는 §4-2 의 문장으로 무엇을 뺐는지 말한다).
  유명 상표 배너가 이름 쪽의 강한 일치로 뜬 질의에서도 그리지 않는다(위).
- **접근성**: 큰 안내에는 보이는 제목(결과가 뜨면 맨 위 안내의 제목으로 포커스가 간다), 작은 안내에는 보이지 않는 제목("이름에 든
  누구나 쓰는 말")을 두고 영역에 이름을 붙인다. 펼치는 버튼은 펼침 상태(`aria-expanded`)를 알리고, 안내의 종류는 색만이 아니라 아이콘과
  글자("이름 안내 · 설명하는 말로만 된 이름")로도 구분한다.

### 4-8. 업종은 다르지만 표장이 닮은 후보(`cross_goods`·`cross_goods_more`, 2026-11-26)

문구는 `frontend/lib/crossGoods.ts` 한 곳에 모은다. 판단은 엔진의 것이고(`cross_goods.flagged`) 화면은 새로 판단하지 않는다. 필드가
없으면(업종을 넣지 않은 질의·옛 서버) 아무것도 그리지 않는다.

- **후보 카드** — `cross_goods.flagged` 가 true 인 후보의 카드에 표시 **업종 다름**과 설명 한 줄을 붙인다(카드를 펼치지 않아도 보인다).

| 후보 | 설명 한 줄 |
|---|---|
| 보통 상표 | 표장은 닮았지만 업종이 달라요. 보통은 함께 등록될 수 있어요. 다만 나중에 이 업종으로 넓히면 문제가 될 수 있어요. |
| 유명 상표 표시(`famous_brand`)가 붙은 후보 | 업종은 다르지만 널리 알려진 상표라 문제가 될 수 있어요. |

- **전체 등급 옆 한 줄** — 가장 위 후보(`candidates[0]`)가 그런 후보이고, 유명 상표 바닥이 전체 등급을 정한 것이 아닐 때
  (`overall.famous_floor` 가 true 가 아닐 때): "가장 닮은 상표가 다른 업종에 있어요. 업종이 다르면 함께 등록될 수도 있어요."
- **맨 위 영역의 순서** — 유명 상표 배너 → 설명적 이름 안내 → 전체 등급 칸의 이 한 줄. 기존 두 안내의 조건과 문구는 그대로다
  (§4-6·§4-7).
- **목록 아래 접힌 칸** — 화면이 처음 보여 주는 것은 응답의 `candidates[]`(사용자가 고른 `top_k` 5·10·20, 기본 5)이고 더 보기는 없다.
  `cross_goods_more.candidates` 에 보일 후보가 있으면 목록 아래에 접힌 칸 "업종은 다르지만 표장이 닮은 상표 {N}건"({N} = `count`)을
  두고, 펼치면 그 후보(최대 5개)를 목록과 같은 카드로 보인다. {N} 이 보이는 수보다 많으면 "{N}건 가운데 표장이 가장 닮은 {보이는 수}건을
  보여요." 한 줄을 더한다. 보일 후보가 없으면(범위 안에 다 보이면) 칸을 만들지 않는다.
- **접근성** — 표시는 글자("업종 다름")로 보이고 색만으로 구분하지 않는다. 접힌 칸은 제목으로 이름 붙은 영역이고, 버튼이 펼침 상태
  (`aria-expanded`)와 여는 영역(`aria-controls`)을 알린다.

| 400 | 빈 이미지 — 완전 투명·거의 한 가지 색(전처리 `BlankImageError`; 2026-11-23 부터, 그 전에는 422 + 영어 전처리 문구) | `이미지에서 로고를 찾지 못했어요. 로고가 보이는 이미지를 올려 주세요.` |

| 429 | 한도(`search` 묶음, `MARKLENS_SEARCH_RATELIMIT`) | `요청이 너무 많습니다. 잠시 후 다시 시도하세요. (1분에 10번까지 검색할 수 있어요)` — 괄호의 숫자·단위는 설정한 한도에서(2026-11-23 부터; 그 전 괄호는 slowapi 영어 `허용 한도: 10 per 1 minute`). 다른 엔드포인트도 같은 꼴(`상표명을 확인할`·`발음이 비슷한 상표를 찾을` 등) |

### 5-2. OCR 실패·유형

이미지 OCR(글자 면적 판정)이 실패하면 — 라이브러리 없음·예외·시간 초과(상한 2초) — 500 이 아니라 **진행**한다: `query_type.source =
"fallback"`, `type` 은 이름이 있으면 문자, 없으면 도형, `caveats` 에 `OCR_FALLBACK` 문구. `type_override` 가 있으면 OCR 을 돌리지 않는다.

### 5-3. 축 결측과 모델 한계

- 이미지·상품 축이 null 이면 모델은 그 축 없이 학습한 계수 집합(결측 패턴, v1.3 §7-3)으로 계산한다(결측은 비유사가 아니다). 축을
  하한값(현실 분포 비유사 평균) 이상으로 더 관측하면 `prob` 는 내려가지 않고, 하한 아래(비유사 평균보다 덜 비슷한 이미지·겹치지 않는
  상품)면 내려갈 수 있다 — 음의 증거. v1.2.1 의 "입력을 더 주면 내려가는" 결측 지시변수 편향은 없다.
- 이미지만(또는 이미지+지정상품) 입력하면 이름 없는 계수 집합이 이미지 유사도로 위험도를 내고(v1.4, §2-4 1·2항), 등급은 그 집합의
  하한으로 매긴다 — 같은 로고(이미지 1.0)는 0.634 로 "위험"(§3-2). v1.3 까지는 이미지만 넣으면 `prob` 0.05 안팎이라 등급이 도형 규칙으로만
  올랐다. 지정상품만 입력하면 `x4` 뿐이라 `prob` 는 최대 0.08 안팎(패턴 `x4` 절편 -3.4535 + x4 0.9583) → "안전"이 상한이다. 두 경우 모두
  `caveats` 로 알린다.
- "위험" 정밀도 0.70(이름 있는 판단, v1.3; v1.2.1 0.69) 은 검증 데이터(경계 사례 심결 + 쉬운 음성) 기준이며 서비스 분포의 정확도가 아니다(README "경계 사례 데이터").
  이름 없는 판단에는 이 정밀도 문구를 쓰지 않는다(§4-3).
- 유명 상표 확인(§2-6)은 등록부의 브랜드(현재 58개)만 본다 — 일치가 없다는 것은 "목록의 브랜드와 닮지 않았다"는 뜻이지 유명 상표와
  무관하다는 뜻이 아니다(화면 각주). 확인 중 예외가 나면 검색 결과는 그대로 나가고 `famous.status` 가 `unavailable` 이다(전체 등급에
  바닥이 반영되지 않은 응답 — 화면은 "유명 상표 확인을 하지 못했어요." 한 줄).

### 5-4. 후보 0건

후보 풀이 비면(이름에 호칭·관념이 없고 이미지도 없음, 또는 모든 축의 하한 미달) `candidates: []`, `overall.grade: null`,
`overall.prob: null`, `caveats` 에 `NO_CANDIDATES`(+ 해당 `NO_*`), `meta.pool.total: 0` 으로 **200** 을 돌려준다.

### 5-5. v1 엔드포인트

이미지 검색 v1 `POST /search`(이미지 4상태)와 BFF `/api/search`, gateway `location = /api/search`, v1 결과 화면은 **2026-11-21
제거**했다(v2 로 일원화 — 공개 배포 전이라 외부 사용자 없음). 시각 4상태는 v2 `overall.visual_status` 로 그대로 나가고, v1 응답의
deprecated 필드(`grade_code`·`grade_name`)도 함께 없어졌다. `POST /phonetic-search`·`POST /semantic-search` 와 BFF
`/api/phonetic-search`·`/api/semantic-search` 는 상표명 확인 패널의 발음·관념 섹션이 쓰는 별개 흐름이라 **상표명 확인
패널용 엔드포인트로 유지**한다(2026-11-21 결정 — 최종 발표 뒤 제거하려던 계획은 철회).

### 5-6. 엔진 예외 ↔ HTTP (B-1 매핑 기준, 2026-10-24 구현)

`engine.multi_search(image=None, name=None, goods_codes=None, type_override=None, top_k=5)` 는 동기 함수이고
`SearchV2Result`(`to_dict()` 가 §2 키 그대로)를 돌려준다. 예외 이름은 `backend/src/core/multi_search.py`.

| 예외 | 언제 | 메시지(그대로 `detail` 로) | HTTP |
|---|---|---|---:|
| `multi_search.EmptyQueryError`(ValueError) | `image`·`name`(공백만 포함)·`goods_codes`(빈 값만 포함)가 모두 없음 | `image, name, goods_codes 중 하나는 있어야 합니다.` | 400 |
| `ValueError` | `top_k` 가 1–20 밖, `type_override` 가 문자·도형·결합 밖 | `top_k 는 1~20 정수여야 합니다 (받은 값: …).` / `type_override 는 문자·도형·결합 중 하나여야 합니다.` | 422 |
| `multi_search.ModelNotReadyError`(RuntimeError) | 계수 JSON(기본 `shared/model/risk_model_v1.4.7.json`, `meta.grade_precision` 포함) 또는 식별력 모델을 기동 때 못 읽음, 또는 계수 JSON 이 유명 상표 확인을 켰는데 그 자료(등록부·확정 파일·대표 로고 구분 파일)가 없거나 깨졌거나 해시가 다름(v1.4.7) — 서버는 떠 있고 이 기능만(`/health` 도 503, §5-7) | **그대로 내지 않는다** — 고정 문구 `위험도 모델을 준비하지 못했어요. 잠시 뒤 다시 시도해 주세요.`. 원인(`multi_search.state.error` — 파일 경로·예외 원문)은 기동 때 서버 로그에만(2026-11-23, 견고성 점검 R-P1-3; 그 전에는 원인 목록을 `detail` 로) | 503 |
| `RuntimeError` | 엔진(인덱스·CLIP) 미준비 | `Engine 이 아직 초기화되지 않았습니다.` | 503 |

### 5-7. 상태 확인 `GET /health` — 검색을 할 수 있을 때만 200 (2026-11-23, 견고성 점검 R-P1-2)

통합 검색(`POST /search/v2`)을 할 수 있으면 200, 할 수 없으면 **503** 과 이유 코드(`reason`)를 낸다. 응답에는 내부 경로·예외
원문을 넣지 않는다(원인은 서버 기동 로그). 그 전에는 계수 JSON 이 없거나 깨져도 `status: "ok"`·200 이었다.

| 필드 | 뜻 |
|---|---|
| `status` | `ok`(검색 가능) · `loading`(엔진·검색 캐시 적재 전) · `error`(적재 실패) |
| `engine_ready` | 엔진(색인·CLIP) 준비 — 예전과 같은 뜻 |
| `search_ready` | 통합 검색을 할 수 있음. false 면 HTTP 503 |
| `reason` | 검색을 할 수 없는 이유 코드, 할 수 있으면 null: `ENGINE_LOADING` · `INDEX_EMPTY` · `SEARCH_LOADING` · `RISK_MODEL_UNAVAILABLE`(계수 JSON 없음·깨짐·검증 실패) · `DISTINCTIVENESS_UNAVAILABLE`(식별력 모델) · `FAMOUS_CHECK_UNAVAILABLE`(v1.4.7 — 계수 JSON 이 유명 상표 확인을 켰는데 등록부 `shared/famous_registry.json`·확정 파일 `shared/famous_check_confirmed.json`·대표 로고 구분 파일 `shared/famous_logo_kinds.json` 이 없거나 깨졌거나, 확정 파일의 해시가 계수 JSON 에 적힌 값과 다르거나, 등록부의 해시가 확정 파일에 적힌 값과 다름) · `CANDIDATES_UNAVAILABLE`(후보 캐시) |
| `index_size`·`trademark_count`·`storage_mode`·`artifact_generation_id` | 예전과 같음 |

- 상품↔유사군 변환표(`/goods/*`)나 관념 검색(`/semantic-search`)만 못 쓰는 경우는 통합 검색에 지장이 없어 200 이다(그 엔드포인트만 503).
- 기동 중(lifespan 의 모델 적재)에는 서버가 아직 연결을 받지 않아 503 이 아니라 연결 실패다 — 엔진은 기동 뒤 다시 적재하지 않는다.
- 배포: `deploy/backend.Dockerfile` 의 HEALTHCHECK 는 200 이 아니면 실패로 센다(`--start-period=180s` 안의 실패는 세지 않고, 그 뒤 3번
  연속이면 unhealthy). compose 의 `restart: unless-stopped` 는 프로세스가 끝날 때만 다시 띄우고 unhealthy 로는 재시작하지 않는다 — 모델
  적재 중이나 모델 파일 문제로 재시작이 되풀이되지 않는다. 계수 JSON 이 깨진 채 배포하면 backend 가 unhealthy 가 되어
  `depends_on: condition: service_healthy` 인 frontend 가 뜨지 않는다(배포 단계에서 알아챔). CI 는 `/health` 를 쓰지 않는다.
- 프런트 BFF `GET /api/health` 는 백엔드가 200 이 아니면 그 상태 코드로 `서비스 상태를 확인할 수 없어요.` 를 낸다(이유 코드는 넘기지
  않음) — 프런트 컨테이너 HEALTHCHECK 도 검색 불가를 알아챈다.
