## 0. 배경 — 지금 어디까지 와 있나

- 백엔드-5(`backend/scripts/collect_pipeline.py`)는 **출원인 검색 → 이미지 즉시 다운로드 → DB UPSERT → 인덱스 재빌드**를 한 명령으로 도는 상태. TODO 필수 4요건(호출 카운터·초당 딜레이 / 일회성 링크 즉시 다운로드 / 등록만 / 비엔나 빈값 제외)은 코드에 반영되어 있고, mock XML 오프라인 검증까지 통과했다.
- 현재 DB는 실데이터 100건(더미 정리 후) 수준. scoring.py 임계값 재보정은 **실데이터 500건 이후**로 미뤄져 있다(더미 10건 보정은 무의미).
- 백엔드-6은 이 파이프라인으로 **DB를 500~1,000건으로 키우는 작업**이다. 관건은 데이터 품질/편중이 아니라 **월 1,000회 쿼터를 태우지 않고 목표 건수에 도달**하는 것.

### ✅ 본 수집 전 닫아야 했던 코드 공백 [해소 — 2026-07-09]

감사보고서(§횡단리스크·6-2)가 백엔드-5 DoD로 못박았던 세 가지. **`collect_pipeline.py`에 구현 완료**되어 본 수집의 코드 측 선결 조건은 해소되었다(오프라인 테스트 5건으로 검증, KIPRIS 실호출 0회).

1. **레코드별 체크포인트** — 수집 완료 출원번호를 `ml/data/collect_checkpoint.json`에 원자적으로 기록. 중단(Ctrl-C·예외·쿼터 소진) 후 재실행 시 이어받는다.
2. **기수집 출원번호 skip** — 체크포인트 ∪ DB ∪ 이미지 실물 중 하나라도 있으면 검색 결과에서 건너뛴다(리포트에 `건너뜀_기수집` 집계). 재수집이 필요하면 `--force`.
3. **파싱 전 원본(XML·이미지) 디스크 선저장** — 검색 응답 XML을 파싱 이전에 `ml/data/raw_kipris/collect/xml/`에 저장하고, 이미지는 행 변환 이전에 저장한다. `ImagePath`는 일회성 링크라 파싱 버그로 재수집하면 링크가 만료돼 호출을 또 태우기 때문. 저장된 원본은 `--mock-xml`로 재파싱할 수 있다.
   - **`--dry-run`도 검색 API를 호출해 쿼터를 태우므로 원본을 저장한다.** dry-run을 "공짜 미리보기"로 오해하지 말 것.

> 남은 선결 조건은 코드가 아니라 **KIPRIS 상품 승인**(현재 대기, resultCode 31)과 **수집 기준 단톡 합의**다. 승인 후 아래 ⓓ 체크리스트대로 5건 파일럿부터.

| **류 편중 방지** | 특정 류 비중 상한 + 다양한 업종 출원인 선정 | [잠정] 아래 참조 |

### 류 편중 방지 방법 [잠정]

유명 브랜드 출원인만 쓸어 담으면 IT/식음료 등 몇 개 류에 쏠린다. 외관 검색은 류에 직접 의존하진 않지만, 편중 데이터로 임계값을 보정하면 왜곡될 수 있다.

- **수집 중 류 분포를 리포트**한다(수집 리포트에 류별 건수 추가 — collect_pipeline 보강 항목).
- **단일 류 상한**: 한 류가 전체의 일정 비율(예: 25% [잠정])을 넘기면 해당 류 편중 출원인은 뒤로 미룬다.
- **업종 다양성**: 프론트-3 브랜드 목록을 IT / 식음료 / 패션 / 유통 / 제조 등 **업종 버킷**으로 나눠 고르게 뽑는다(목록 확정 후 협의).

### 건당 호출 수 추정 [잠정 — 파일럿에서 실측 확정]

감사보고서는 **건당 2~4회**로 잡았다. 실제 산수는 오퍼레이션 구성에 달렸다:

- **출원인 검색 1회 → 여러 건 반환**(검색 호출은 출원인당 1회, 레코드당 아님)이라 검색 호출은 크게 상각된다.
- 이미지 다운로드(`download_file_now`)는 `fileToss.jsp` 파일 링크로, **현재 코드상 월 카운터에 잡히지 않는다**(검색 `_get`만 리미터 통과). 다만 KIPRIS가 다운로드도 쿼터에 산입하는지는 **파일럿에서 실측 필요**.
- 영문명·상세 서지 등 보강 필드가 필요하면 **레코드별 상세 조회 1회**가 추가될 수 있다(현재 미구현).

> **결론: "건당 2~4회"는 상한 가정으로 두고, 5건 파일럿에서 카운터 증가분(`kipris_call_count.json`)을 실측해 확정한다.**

### 월별 페이스 (승인월 기준 상대 계획) [잠정]

승인 시점이 미정이라 달력이 아니라 **승인월(M+0)** 기준으로 잡는다. 건당 3회(중간 가정)·예산 950 기준:

| 시점 | 목표 누적 | 그 달 호출(≈) | 메모 |
|---|---|---|---|
| **M+0** (승인 직후) | 5 → 150건 | ~450 | 파일럿 5건 실측 → 소규모 배치. 예산 절반 이하로 보수적 |
| **M+1** | ~450건 | ~900 | 페이스 정상화. 류 분포 점검·리밸런싱 |
| **M+2** | **500~1,000건 도달** | ~900 | 목표 하한(500) 우선, 여유 있으면 상한(1,000)까지 |

- 로드맵상 백엔드-6은 **M3(8/17~8/30)** 창이지만, 위 표는 승인 지연에 우아하게 열화하도록 상대 시점으로 둔다.
- **한 달에 다 태우지 않는다** — 링크 만료·파싱 버그 재호출 대비 예비를 남긴다. 카운터가 800 근처면 그 달은 멈추고 다음 달 이어받는다(체크포인트 전제).

## ⓒ 유명 로고 브랜드 출원인 일괄 검색 연계 절차

> **의존: 프론트-3 브랜드 목록(8/8 마감) 대기 중.** 목록 확정 전에는 절차만 고정한다.

1. **프론트-3 목록 수령** → 브랜드명 리스트.
2. **브랜드명 → 출원인명 매핑** (핵심 주의점): 브랜드명과 KIPRIS 출원인명은 다르다(예: 브랜드 "갤럭시" → 출원인 "삼성전자 주식회사"). 출원인 필드로 검색하므로 **브랜드→법인 출원인명 매핑표**가 필요하다. 이 매핑은 프론트-3 목록과 함께 팀에서 확정한다(법인명 표기 흔들림 — "(주)"/"주식회사"/영문 병기 — 도 정규화).
3. **출원인 목록 파일 작성**: 줄당 출원인 1개, `#` 주석 지원 → `shared/famous_brands.txt` [잠정 경로].
4. **오프라인 예행**: `collect_pipeline --applicants-file <파일> --dry-run` (실호출 없이 인자·경로 검증. 실제로는 dry-run도 검색 호출은 하므로, 승인 전에는 `--mock-xml`로만).
5. **일괄 실호출**: 승인·파일럿 통과 후 `--applicants-file <파일> --skip-index` 로 배치 수집(인덱스는 **마지막 1회만** 재빌드). 출원인 간 **중복 출원번호는 기수집 skip**으로 걸러진다(공백 항목 2 선행 필요).
6. **출원인당 상한**: `--limit N` 으로 특정 대기업이 수백 건을 독식하지 않게 제한(류 편중 방지와 연동).

## ⓓ 실행 전 체크리스트

**1단계 — 키 승인 확인**
- [ ] `plus.kipris.or.kr` 마이페이지 > 오픈API 신청현황 **처리상태 "사용중"** 확인.
- [ ] `.env` 에 `KIPRIS_ACCESS_KEY` + 오퍼레이션 URL/파라미터 설정(커밋 금지).
- [ ] 승인 검증: 소규모 검색 1회 → **resultCode 31(승인 대기)이 아니어야** 통과. 31이면 아직 미승인(클라이언트가 마이페이지 확인 안내 문구를 낸다).

**2단계 — 코드 공백 선(先)보강** (§0 참조)
- [ ] 체크포인트 / 기수집 skip / 원본 선저장 3종 구현·테스트.
- [ ] 수집 리포트에 **류 분포** 추가.

**3단계 — 소규모 5건 파일럿**
- [ ] 오프라인 예행: `--mock-xml` 로 파싱·필터 확인(네트워크 0).
- [ ] 실호출 파일럿: 출원인 1개 `--limit 5` 로 **실 5건** 수집.
- [ ] 검증: DB 5건 적재 · 이미지 5장 실물 · reconcile 불변식("DB에 있으면 이미지도 있다") · **`kipris_call_count.json` 증가분 = 건당 호출 수 실측** → ⓑ 표 보정.

**4단계 — 본 수집**
- [ ] 월 예산 페이스(ⓑ) 준수 — 카운터 모니터링.
- [ ] 배치 후 인덱스 1회 재빌드(`--skip-index` 후 마지막에).
- [ ] 류 분포 점검 → 편중 시 리밸런싱.

## ⓔ "데이터 범위 안내 문구" 갱신 항목

수집이 끝나면 **사용자에게 노출되는 데이터 범위 안내**(dataset_info)를 실제 수집 결과로 갱신해야 한다. collect_pipeline도 종료 시 이를 리마인드한다("백엔드-6 기준 확정 후 meta 테이블에서 갱신").

| 필드 | 갱신 내용 |
|---|---|
| `총_상표수` | 실제 DB 적재 건수(reconcile 후) — 안내 문구와 실건수 불일치 금지 |
| `출원일자_범위` | 실제 min/max 출원일자(예: "2016 ~ 2026") |
| `데이터_기준` | "전체 등록상표"가 아님을 명시 — 예: "최근 10년 등록 **도형/복합상표**, 유명 브랜드 출원인 중심 표본" |
| `생성일자`/갱신일자 | 수집 완료일 |

**오인 방지 문구(중요)** [잠정 — 법리(다빈)·프론트 협의]: 이 DB는 **전체 상표가 아니라 표본**이다. "검색 결과 없음 = 충돌 없음"으로 읽히면 안 된다. 프론트 결과 화면 하단에 *"본 서비스 데이터는 전체 등록상표의 일부(표본)이며, 결과가 없어도 실제 선행상표가 없다는 뜻은 아닙니다"* 류의 단서를 노출한다(설계결정기록 "단정 금지" 원칙과 연동).
