## 0. 배경 — 지금 어디까지 와 있나

- 백엔드-5(`backend/scripts/collect_pipeline.py`)는 **출원인 검색 → 이미지 즉시 다운로드 → DB UPSERT → 인덱스 재빌드**를 한 명령으로 도는 상태. TODO 필수 4요건(호출 카운터·초당 딜레이 / 일회성 링크 즉시 다운로드 / 등록만 / 비엔나 빈값 제외)은 코드에 반영되어 있고, mock XML 오프라인 검증까지 통과했다.
- 현재 DB는 실데이터 100건(더미 정리 후) 수준. scoring.py 임계값 재보정은 **실데이터 500건 이후**로 미뤄져 있다(더미 10건 보정은 무의미).
- 백엔드-6은 이 파이프라인으로 **DB를 500~1,000건으로 키우는 작업**이다. 관건은 데이터 품질/편중이 아니라 **월 1,000회 쿼터를 태우지 않고 목표 건수에 도달**하는 것.

### ✅ 본 수집 전 닫아야 했던 코드 공백 [해소 — 2026-07-09]

감사보고서(§횡단리스크·6-2)가 백엔드-5 DoD로 못박았던 세 가지. **`collect_pipeline.py`에 구현 완료**되어 본 수집의 코드 측 선결 조건은 해소되었다(오프라인 테스트 5건으로 검증, KIPRIS 실호출 0회).

1. **레코드별 체크포인트** — **DB UPSERT 성공 후에만** 출원번호를 `ml/data/collect_checkpoint.json`에 원자적으로 기록한다. 중단(Ctrl-C·쿼터 소진) 시에도 그때까지 확보한 행을 먼저 적재하고 종료 코드 3으로 끝내므로, 재실행이 이어받을 때 체크포인트와 DB가 어긋나지 않는다.
   - *(2026-07-10 수정)* 처음엔 레코드마다 체크포인트를 먼저 쓰고 적재는 루프 끝에 한 번 했다. 그러면 예산 소진으로 중단될 때 체크포인트·이미지는 남고 DB 적재만 빠져서, **재실행이 그 레코드들을 skip 해 영원히 적재되지 않았다.** 500건 보강이 바로 그 시나리오였다.
2. **기수집 출원번호 skip** — **DB ∪ 체크포인트**(=적재 완료)에 있으면 건너뛴다(리포트에 `건너뜀_기수집`). **이미지 실물 존재는 skip 근거가 아니다** — 이미지는 적재보다 먼저 저장되므로 "이미지 있음 ≠ 적재됨"이다. 이미지가 이미 있으면 **다운로드만 건너뛰고 적재는 진행**한다(`이미지_재사용` 집계, 만료된 일회성 링크 재호출 방지). 재수집이 필요하면 `--force`.
3. **파싱 전 원본(XML·이미지) 디스크 선저장** — 검색 응답 XML을 파싱 이전에 `ml/data/raw_kipris/collect/xml/`에 저장하고, 이미지는 행 변환 이전에 저장한다. `ImagePath`는 일회성 링크라 파싱 버그로 재수집하면 링크가 만료돼 호출을 또 태우기 때문. 저장된 원본은 `--mock-xml`로 재파싱할 수 있다.
   - **`--dry-run`도 검색 API를 호출해 쿼터를 태우므로 원본을 저장한다.** dry-run을 "공짜 미리보기"로 오해하지 말 것.

> **KIPRIS 상품 승인**(2026-07-09 확인)과 **본 수집 오퍼레이션(getAdvancedSearch) 확보·구현**(§ⓑ 결정 3)까지 끝나, 남은 선결 조건은 **수집 기준 단톡 합의**(특히 `50/51/56` 정책)와 **실 파일럿**뿐이다. 아래 ⓓ 체크리스트대로 5건 파일럿부터.

유명 브랜드 출원인만 쓸어 담으면 IT/식음료 등 몇 개 류에 쏠린다. 외관 검색은 류에 직접 의존하진 않지만, 편중 데이터로 임계값을 보정하면 왜곡될 수 있다.

### ✅ 본 수집 경로(getAdvancedSearch) 수율 실측 [확정 — 2026-07-09, 호출 3회 추가 소모(누적 5/950)]

출원인 검색 오퍼레이션 URL을 확보(§ⓑ 결정 3 해소)하고, **항목별검색 `getAdvancedSearch`** 로 `applicantName=삼성전자`를 서버측 필터(등록만·도형/도형복합만·표장유형 전부)와 함께 질의한 결과다. 이 오퍼레이션은 상표명완전일치와 **다른 API 계열**(kipo-api/kipi, 인증 `ServiceKey`, camelCase 응답)이며, 불리언 플래그 30개를 전부 실어야 동작한다. 원본은 저장해 두어 추가 호출 없이 재분석 가능하다.

| 단계 | 건수 |
|---|---|
| 검색 결과 (`totalCount`) | **630** |
| 한 번의 호출로 수신 (`numOfRows`=500, 공식 상한) | **500** (전부 `applicationStatus`="등록") |
| 제외: 출원번호가 40/41 아님(`45`×15·`50`×18·`51`×12·`56`×10·`70`×2) | 57 |
| **실제 적재 대상** | **443건 / 500건 (수율 89%)** |

- **수율 3% → 89% 로 개선(실측).** 상표명완전일치는 소멸·거절이 75%라 59건 중 2건(3%)만 적재됐는데, 출원인+서버측 등록/도형 필터를 쓰는 getAdvancedSearch는 500건 중 443건을 적재한다. 서버가 미등록/문자상표를 걸러주므로 클라이언트 `제외_미등록`·`제외_비엔나없음`은 0에 수렴한다(리포트상 정상).
- **페이징 확정**: 요청 파라미터는 `pageNo` / `numOfRows`(기본 30, **최대 500**). 코드는 항상 500으로 받고 `totalCount` 를 다 채울 때까지 `pageNo` 를 올린다. 630건 출원인이면 **2회 호출**로 끝난다(20건씩 받으면 32회). 상표명완전일치 계열의 `docsStart`/`docsCount` 와 이름이 다르다.
- **`similarityCode`(유사군) 필드가 응답에 없다.** 요청 파라미터로는 존재하지만(유사군으로 검색은 가능) 응답에는 안 온다 → `similarity_codes` 는 빈 배열로 적재하고, **서지정보 오퍼레이션으로 후속 보강해야 한다**(X4 축과 다빈-1 라벨표 학습이 여기 걸려 있다).
- `drawing`(이미지경로)/`bigDrawing`(큰이미지경로) 은 항목마다 고유한 `fileToss.jsp` **일회성 링크** — 코드가 즉시 다운로드한다(bigDrawing 우선).

**여기서 나오는 결정 사항 3가지:**

1. **[미정 — 팀 결정 필요, 근거 확보됨] `45/50/51/56/70` 접두를 계속 버릴 것인가.**
   `is_trademark_application_number()` 는 40/41만 통과시킨다. 근거는 *심판 API 응답에 특허(10…)가 섞인다*(`appno.py`)였는데, **공보 검색에서는 이 화이트리스트가 정상 상표를 버린다.**

   등록 도형상표 500건 표본의 **출원번호 접두 × 등록번호 접두** (2026-07-09 실측):

   | 출원번호 접두 | 건수 | 출원연도 | **등록번호 접두** | 판정 |
   |---|---:|---|---|---|
   | `40…` | 374 | 1976~2025 | 40 | 상표 — 채택 |
   | `41…` | 69 | 1986~2016 | 41 | 서비스표 — 채택 |
   | `45…` | 15 | 2000~2016 | 45 | **상표/서비스표(문서상 코드 45)** — 버려짐 |
   | `50…` | 18 | 1987~2003 | **40** | 상표로 등록된 권리 — 버려짐 |
   | `51…` | 12 | 1998~2000 | **41** | 서비스표로 등록된 권리 — 버려짐 |
   | `56…` | 10 | 2003 | **40** | 상표로 등록된 권리 — 버려짐 |
   | `70…` | 2 | 2019~2020 | **40** | 상표로 등록된 권리 — 버려짐 |

   즉 **50/51/56/70 은 특허가 아니다 — 등록번호가 40/41 인 정식 상표·서비스표다.** (마드리드 가설도 기각: `internationalMark` 플래그를 꺼도 이 접두들이 그대로 남았다.) 현행 정책은 표본의 **8.4%(42/500)** 를, `45` 까지 합치면 **11.4%(57/500)** 를 근거 없이 버린다.

   **제안**: 화이트리스트(40/41)를 **블랙리스트(특허 10 / 실용신안 20 / 디자인 30 제외)** 로 바꾼다 — 원래 목적("심판 API에 섞인 특허 배제")은 그대로 달성하면서 정상 상표를 잃지 않는다. `appno.NON_TRADEMARK_PREFIXES` 상수를 미리 넣어 두었다. **동작 변경은 팀 합의 후.** 현행 코드는 40/41만 통과(무변경).
2. **[확정] 상표명완전일치는 본 수집 소스로 부적합.** 결과의 75%가 소멸·거절이다. 이 오퍼레이션은 백엔드-7(`/name-check`, "동일 명칭 선행상표 N건") 용도로 쓰고, 본 수집은 **출원인 항목별검색(getAdvancedSearch)** 으로 간다.
3. **[해소 — 2026-07-09] 출원인 검색 오퍼레이션 URL 확보 완료.** 본 수집 소스는 상표명완전일치가 아니라 **`getAdvancedSearch`**(`http://plus.kipris.or.kr/kipo-api/kipi/trademarkInfoSearchService/getAdvancedSearch`)다. 인증 파라미터가 `accessKey`가 아니라 **`ServiceKey`**이고, 불리언 플래그 30개(행정상태 8 + 표장유형 9 + 표장구성 13)를 전부 실어야 한다(일부만 넘기면 resultCode=10). URL은 `KIPRIS_BASE_URL` + 경로 상수로 코드가 자동 조합하므로 **`.env`에 URL을 넣지 않아도 동작**한다(오버라이드는 `KIPRIS_APPLICANT_SEARCH_URL`로 계속 지원). 클라이언트는 `kipris_client.advanced_search()`로 구현·오프라인 검증 완료.

> 수율이 3% → 80%로 오르면서 ⓑ 페이스 계획도 완화된다 — **"검색 호출 수"가 아니라 "적재 건수"로 예산을 잡되**, 적재당 검색 상각이 커졌다. 출원인 검색의 실제 수율은 파일럿에서 다시 잰다(브랜드 출원인은 도형 등록상표 비율이 높을 것으로 기대되나 삼성전자 1건 표본이므로 **아직 가정**이다).

### 건당 호출 수 추정 [잠정 — 파일럿에서 실측 확정]

감사보고서는 **건당 2~4회**로 잡았다. 실측(수율 80%)으로 이 상한 가정은 **보수적**임이 드러났다. 실제 산수는 오퍼레이션 구성에 달렸다:

- **출원인 검색 1회 → 최대 500건 반환**(검색 호출은 페이지당 1회, 레코드당 아님)이라 검색 호출은 크게 상각된다. 실측: 500건 수신 중 **443건(89%)이 적재 대상** ⇒ **적재당 검색 호출 ≈ 0.002회**. 검색은 더 이상 예산의 병목이 아니다.
- **페이징 확정**(`pageNo`/`numOfRows`, 최대 500). 코드는 `totalCount` 를 다 받을 때까지 페이지를 이어받고, 페이지마다 원본 XML을 따로 선저장한다(DoD Ⓐ). 출원인당 페이지 상한 10(=5,000건)을 두어 폭주를 막는다.
- 이미지 다운로드(`download_file_now`)는 `fileToss.jsp` 파일 링크로, **현재 코드상 월 카운터에 잡히지 않는다**(검색 `_get`만 리미터 통과). 다만 KIPRIS가 다운로드도 쿼터에 산입하는지는 **파일럿에서 실측 필요**.
- **유사군(similarityCode) 보강 경로 확보·구현 [해소 — 2026-07-10]**: 서지상세 `getBibliographyDetailInfoSearch`(출원번호 1개 → 유사군·지정상품·비엔나·서지요약)를 클라이언트에 구현하고(`kipris_client.bibliography_detail`), 수집 파이프라인에 **옵트인 플래그 `--enrich-biblio`** 로 붙였다. **레코드당 +1회 호출**이라 500건 보강 = **+500회(월 예산 950의 절반)** — 기본은 꺼짐. 실제 증가분은 파일럿에서 실측한다. 영문명·상세 서지는 여전히 미구현(후속).

> **결론: "건당 2~4회"는 상한 가정으로 두고, 5건 파일럿에서 카운터 증가분(`kipris_call_count.json`)을 실측해 확정한다. 수율 80%·검색 상각(적재당 ≈0.06회)을 감안하면 500~1,000건 목표는 예산 950회 안에서 여유롭게 도달 가능하다(단, 페이징 확장·이미지 쿼터 산입 여부가 변수).**

### 월별 페이스 (승인월 기준 상대 계획) [잠정]

승인 시점이 미정이라 달력이 아니라 **승인월(M+0)** 기준으로 잡는다. 건당 3회(중간 가정)·예산 950 기준:

| 시점 | 목표 누적 | 그 달 호출(≈) | 메모 |
|---|---|---|---|
| **M+0** (승인 직후) | 5 → 150건 | ~450 | 파일럿 5건 실측 → 소규모 배치. 예산 절반 이하로 보수적 |
| **M+1** | ~450건 | ~900 | 페이스 정상화. 류 분포 점검·리밸런싱 |
| **M+2** | **500~1,000건 도달** | ~900 | 목표 하한(500) 우선, 여유 있으면 상한(1,000)까지 |

- 로드맵상 백엔드-6은 **M3(8/17~8/30)** 창이지만, 위 표는 승인 지연에 우아하게 열화하도록 상대 시점으로 둔다.
- **한 달에 다 태우지 않는다** — 링크 만료·파싱 버그 재호출 대비 예비를 남긴다. 카운터가 800 근처면 그 달은 멈추고 다음 달 이어받는다(체크포인트 전제).

## ⓒ 유명 로고 브랜드 출원인 일괄 검색 연계 절차

> **의존: 프론트-3 브랜드 목록(8/8 마감) 대기 중.** 목록 확정 전에는 절차만 고정한다.

1. **프론트-3 목록 수령** → 브랜드명 리스트.
2. **브랜드명 → 출원인명 매핑** (핵심 주의점): 브랜드명과 KIPRIS 출원인명은 다르다(예: 브랜드 "갤럭시" → 출원인 "삼성전자 주식회사"). 출원인 필드로 검색하므로 **브랜드→법인 출원인명 매핑표**가 필요하다. 이 매핑은 프론트-3 목록과 함께 팀에서 확정한다(법인명 표기 흔들림 — "(주)"/"주식회사"/영문 병기 — 도 정규화).
3. **출원인 목록 파일 작성**: 줄당 출원인 1개, `#` 주석 지원 → `shared/famous_brands.txt` [잠정 경로].
4. **오프라인 예행**: `collect_pipeline --applicants-file <파일> --dry-run` (실호출 없이 인자·경로 검증. 실제로는 dry-run도 검색 호출은 하므로, 승인 전에는 `--mock-xml`로만).
5. **일괄 실호출**: 승인·파일럿 통과 후 `--applicants-file <파일> --skip-index` 로 배치 수집(인덱스는 **마지막 1회만** 재빌드). 출원인 간 **중복 출원번호는 기수집 skip**으로 걸러진다(공백 항목 2 선행 필요).
6. **출원인당 상한**: `--limit N` 으로 특정 대기업이 수백 건을 독식하지 않게 제한(류 편중 방지와 연동).

## ⓔ "데이터 범위 안내 문구" 갱신 항목

수집이 끝나면 **사용자에게 노출되는 데이터 범위 안내**(dataset_info)를 실제 수집 결과로 갱신해야 한다. collect_pipeline도 종료 시 이를 리마인드한다("백엔드-6 기준 확정 후 meta 테이블에서 갱신").

| 필드 | 갱신 내용 |
|---|---|
| `총_상표수` | 실제 DB 적재 건수(reconcile 후) — 안내 문구와 실건수 불일치 금지 |
| `출원일자_범위` | 실제 min/max 출원일자(예: "2016 ~ 2026") |
| `데이터_기준` | "전체 등록상표"가 아님을 명시 — 예: "최근 10년 등록 **도형/복합상표**, 유명 브랜드 출원인 중심 표본" |
| `생성일자`/갱신일자 | 수집 완료일 |

**오인 방지 문구(중요)** [잠정 — 법리(다빈)·프론트 협의]: 이 DB는 **전체 상표가 아니라 표본**이다. "검색 결과 없음 = 충돌 없음"으로 읽히면 안 된다. 프론트 결과 화면 하단에 *"본 서비스 데이터는 전체 등록상표의 일부(표본)이며, 결과가 없어도 실제 선행상표가 없다는 뜻은 아닙니다"* 류의 단서를 노출한다(설계결정기록 "단정 금지" 원칙과 연동).
