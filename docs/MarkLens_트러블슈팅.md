## TS-01. 로컬 환경의 상표 데이터가 전부 합성 더미 + DB에 더미 잔존

- **날짜/해결자**: 2026-07-09 / 정현수 · **심각도**: 높음 (검색 결과가 전부 가짜)
- **증상**: 검색을 돌리면 "더미상표1~9"만 나옴. 새 컴퓨터에서 클론했더니 실데이터가 없음.
- **원인 규명**:
  1. `ml/data/kipris_metadata.json`을 열어보니 `"데이터_기준": "합성 더미 데이터"` 명시 — 실데이터가 아니라 기능 검증용 10건.
  2. 실데이터(이미지·인덱스·원시 txt/PDF)는 저작권 때문에 `ml/data/` 통째로 gitignore — **git 클론으로는 절대 안 따라온다.** 팀 공유 압축본에서 받아야 함(TODO.pdf 참고 박스).
  3. 실데이터 100건을 마이그레이션했는데 DB 검증이 "109건 → OK"를 찍음 — **마이그레이션은 UPSERT만 하고 잔존 행을 지우지 않아서** 이전 더미 9건이 그대로 남았고, 검증 로직이 이를 통과시켰다.
- **조치**: 공유 압축본의 `ml/data`를 배치(기존 더미는 `tmp/`에 백업) → 마이그레이션 → 더미 9건 수동 삭제. 재발 방지로 `migrate_json_to_db`에 **잔존 행 검출 리포트 + `--prune` 옵션** 추가(JSON에 없는 DB 행을 찾아 보고/삭제).
- **검증**: DB 정확히 100건, 표본이 실제 등록상표(엔지유몰 휴식 등). 자기일치 검색 유사도 1.0.
- **교훈**: gitignore된 데이터는 "코드 = 전부"라는 직관을 배신한다. **새 환경 셋업 절차에 "공유 압축본 배치"가 반드시 들어가야 하고**, 마이그레이션 검증은 "건수 ≥ 기대"가 아니라 "건수 == 기대 + 잔존 0"이어야 한다.

## TS-02. KIPRIS 수집 수율 3% — 오퍼레이션 교체로 89%

- **날짜/해결자**: 2026-07-09 / 정현수 · **심각도**: 높음 (월 쿼터 1,000회로 목표 500~1,000건 달성 불가 수준)
- **증상**: 상표명완전일치 검색으로 "삼성전자" 59건을 받았는데 우리 필터를 통과한 적재 대상이 **2건(3%)**. 이 수율이면 쿼터를 다 태워도 목표 건수에 못 미침.
- **원인 규명**:
  1. 원본 XML을 저장해두고 오프라인 분석(추가 호출 0회): 59건 중 44건이 소멸·거절, 11건이 비엔나코드 없음(문자상표). **오퍼레이션이 서버측 필터를 지원하지 않아서** 버릴 것까지 다 받아온 것.
  2. API 통합설명서에서 항목별검색 `getAdvancedSearch` 발견 — 행정상태·표장유형·표장구성 필터를 **서버가 걸어줌**.
  3. 전환 과정의 함정 셋 (전부 실측으로 확정):
     - 경로가 다름: 기존 `openapi/rest/…`가 아니라 **`kipo-api/kipi/…`** (같은 URL로 치면 400 → `code400.jsp`)
     - 인증 파라미터가 다름: `accessKey`가 아니라 **`ServiceKey`** (키 값은 동일, 파라미터 이름만 다름)
     - **불리언 플래그 30개를 전부** 실어야 함 — 일부만 보내면 `resultCode=10 INVALID_REQUEST_PARAMETER_ERROR`
  4. 페이징도 계열마다 다름: 완전일치는 `docsStart/docsCount`, getAdvancedSearch는 **`pageNo/numOfRows`(최대 500)**.
- **조치**: 수집 소스를 getAdvancedSearch로 전환(등록만+도형/도형복합 서버 필터), 페이지당 500건으로 `totalCount` 소진까지 이어받기. 완전일치는 `/name-check` 용도로 유지.
- **검증**: 같은 출원인 실측 — 500건 수신 전부 "등록", 적재 443건(**89%**). 630건 출원인 기준 호출 32회 → **2회**.
- **교훈**: KIPRIS는 **한 사이트에 서로 다른 API 계열 두 개**가 공존한다(경로·인증·표기·페이징 전부 다름). 새 오퍼레이션을 쓸 땐 문서의 입력값 샘플 URL부터 확보하고, **실호출 1회 → 원본 저장 → 오프라인 분석** 순서로 쿼터를 아껴라. 계열별 명세는 `MarkLens_백엔드6_데이터확장_수집기준_초안.md` 부록 A에 정리해뒀다.

## TS-03. 출원번호 40/41 필터가 정상 등록상표 11.4%를 폐기

- **날짜/해결자**: 2026-07-09 발견, 2026-07-10 정책 적용 / 정현수 · **심각도**: 높음 (선행상표 풀 누락 = "충돌 없음" 오답 위험)
- **증상**: 수집 리포트에 `제외_상표번호아님`이 계속 잡힘. 등록 상표인데 출원번호가 `50…`, `51…`, `56…`, `70…`, `45…`로 시작하는 건들이 버려지고 있었음.
- **원인 규명** (가설 → 실험 → 기각/확정):
  1. 기존 필터는 40(상표)/41(서비스표) 화이트리스트. 근거는 "심판 API 응답에 특허(10…)가 섞인다"였음 — **공보 검색에는 맞지 않는 가정.**
  2. *가설 A: 마드리드 국제등록상표?* → `internationalMark` 플래그를 끄고 재검색해도 5x가 그대로 잔존. **기각.**
  3. *결정타: 등록번호 대조.* 500건 표본에서 출원번호 접두별로 **등록번호** 접두를 확인 — `50→40`, `51→41`, `56→40`, `70→40`, `45→45`. 즉 전부 **상표·서비스표로 등록된 정식 권리.** 화이트리스트가 표본의 **11.4%(57/500)** 를 근거 없이 버리고 있었다.
- **조치**: 화이트리스트 → **블랙리스트(특허 10 / 실용신안 20 / 디자인권 30만 제외)** 전환. 원래 목적(특허 혼입 방어)은 그대로 달성하면서 누락 제거. 이의 시 상수 한 줄(`appno.NON_TRADEMARK_PREFIXES`)로 원복 가능.
- **검증**: 테스트 8건 추가(45/50/51/56/70 채택, 10/20/30 거부). 전체 스위트 통과.
- **교훈**: 필터의 **원래 목적**(특허 배제)과 **구현 방식**(40/41만 허용)을 구분하라 — 목적이 정당해도 구현이 과도하면 조용히 데이터를 잃는다. 그리고 "이 번호가 뭐지?"는 추측 대신 **등록번호 같은 교차 필드로 검증**할 수 있다. 참고: 제외 목록의 "디자인(30)"은 도형 로고 상표가 아니라 **디자인권**(물품 외관 보호, 별개 권리)이다 — 유사군·비엔나 체계가 없어 X4 계산이 불가하고, 상표 유사 판단의 비교 대상도 아니다.

## TS-04. 쿼터 소진 시 레코드가 DB에 영영 안 들어가는 조용한 누락

- **날짜/해결자**: 2026-07-10 / 정현수 · **심각도**: 치명 (데이터 무결성 — 에러 없이 누락, 복구 경로 없음)
- **증상**: 코드 리뷰(적대적 검증) 단계에서 발견 — 실전에서 터지기 전에 잡음. 유사군 보강(`--enrich-biblio`, 레코드당 1회 호출)을 켜고 대량 수집하면 예산 소진이 **정상 경로**가 되는데, 그때 일부 레코드가 DB에 안 들어가고 재실행해도 복구되지 않는 구조였음.
- **원인 규명**: 순서 문제 두 개가 겹침.
  1. **체크포인트는 레코드마다 즉시 기록, DB 적재(UPSERT)는 루프가 다 끝난 뒤 한 번.** 예산이 루프 중간에 소진되면 적재 단계에 도달하기 전에 죽는다. 그런데 체크포인트("수집됨" 표시)는 이미 써버렸으므로, **재실행이 그 레코드들을 '이미 수집됨'으로 건너뛰어 영구 누락.**
  2. **"이미지 파일 있음"을 "적재 완료"로 오인.** 이미지는 적재보다 먼저 저장되므로 성립하지 않는 추론 — 이미지만 있고 DB에 없는 레코드도 통째로 skip되어 같은 누락을 낳음.
- **조치**:
  - 체크포인트는 **UPSERT 성공 후에만** 기록.
  - 중단(Ctrl-C·쿼터 소진) 시 죽지 않고 **그때까지 모은 행을 먼저 적재**한 뒤 종료 코드 3으로 끝냄(배치 스크립트가 비정상 종료를 알 수 있게).
  - skip 근거를 **DB ∪ 체크포인트**로 한정. 이미지가 이미 있으면 **다운로드만 건너뛰고 적재는 진행**(`이미지_재사용` 집계 — 일회성 링크 재호출 방지와 누락 방지를 동시에).
  - `--mock-xml`(오프라인 개발)과 `--enrich-biblio`(실 API)의 동시 사용을 인자 파싱 단계에서 거부 — 오프라인인 줄 알고 예산 태우는 사고 방지.
- **검증**: 회귀 방지 테스트 3건(적재 실패 시 체크포인트 미기록 / 이미지만 있는 레코드 적재 진행 / mock+enrich 거부) 포함 전체 스위트 통과.
- **트레이드오프(의도된 것)**: 강제 크래시(정전 등) 시 마지막 배치의 검색·보강 호출이 재실행에서 중복될 수 있음(수 회 수준). "데이터 영구 누락"을 "드문 호출 중복"으로 바꾼 교환.
- **교훈**: **"완료" 마킹은 반드시 영속화(DB 적재)가 성공한 뒤에.** 그리고 "부산물이 존재한다(이미지 있음)"와 "작업이 완료됐다(적재됨)"는 다른 명제다 — skip 로직의 근거를 정확히 하라.

## TS-05. dry-run이 월 쿼터를 태우면서 응답 원본은 버림

- **날짜/해결자**: 2026-07-09 / 정현수 · **심각도**: 중간 (예산 이중 낭비)
- **증상**: `--dry-run`을 "공짜 미리보기"로 생각하기 쉬운데, 실제로는 검색 API를 호출한다(월 쿼터 소모). 그런데 그 응답을 파싱만 하고 버려서, 본 수집 때 **같은 검색을 또 호출**해야 했음.
- **원인**: dry-run 경로에서 원본 선저장이 빠져 있었음 — "미리보기는 아무것도 안 남긴다"는 잘못된 대칭 감각.
- **조치**: dry-run도 응답 원본 XML을 저장하도록 통일. 저장된 원본은 `--mock-xml`로 재파싱해 본 수집 준비에 재사용 가능. 도움말에 "dry-run도 쿼터를 소모한다"를 명시.
- **검증**: dry-run 후 원본 파일 생성 assert 테스트.
- **교훈**: 외부 호출이 유료(쿼터)라면 **모든 경로에서 응답을 먼저 저장**하는 게 기본값이어야 한다. "미리보기니까 안 남긴다"는 파일시스템 관점이지 예산 관점이 아니다.

## TS-06. 검색 응답에 유사군이 없어 X4 축·통합모델 학습 차단

- **날짜/해결자**: 2026-07-10 / 정현수 · **심각도**: 높음 (X4 상품 견련성 축, 다빈-1 라벨표→통합모델 학습의 선결 조건)
- **증상**: 본 수집 소스(getAdvancedSearch) 응답에 유사군 필드가 없음. 요청 파라미터로는 존재(유사군으로 *검색*은 가능)하지만 결과에 안 실려 옴. 도형코드 검색도 마찬가지.
- **원인 규명**: API 통합설명서의 오퍼레이션별 출력 명세를 대조 — 유사군을 응답에 주는 건 두 곳뿐: ① 상표명완전일치(`SimilarCode`, 우리는 `/name-check` 용도) ② **서지상세 `getBibliographyDetailInfoSearch`** (출원번호 1개 → 유사군·지정상품·비엔나(설명 포함)·이미지·등록상태 전부). 실호출 1회로 검증 — `similarityCodeInfoArray`와 지정상품의 `subCode` 집합이 정확히 일치함도 확인.
- **조치**: 서지상세 클라이언트 + 중첩 XML 전용 파서 구현(기존 평면 파서로는 못 읽음), 수집 파이프라인에 **옵트인** `--enrich-biblio`로 연결. **레코드당 1회 호출 = 500건이면 예산 950의 절반**이라 기본 꺼짐.
- **운용 결정(B안)**: 본 수집(8월)은 유사군 없이, **백필은 9월 초 별도 배치** — 월 경계를 타면 예산이 자연 분리되고, 유사군 소비처(X4·백엔드-8·9)가 2학기라 늦지 않으며, 서지상세는 출원번호 기반이라 만료가 없어 분리에 위험이 없다. 파일럿 5건만 켜서 실측.
- **검증**: 합성 픽스처 테스트 15건(파서 경계 포함) + 옵트인 미지정 시 호출 0회 테스트.
- **교훈**: 목록 검색 API와 상세 조회 API는 **주는 필드가 다르다** — 필요한 필드가 응답 명세에 있는지 쓰기 전에 확인하라. 그리고 레코드당 과금되는 보강은 반드시 옵트인 + 예산 경고를 달아라.

## TS-07. 백엔드 서버가 CLIP 로드 중 로그 없이 간헐 사망

- **날짜/해결자**: 2026-07-09 / 정현수 · **심각도**: 중간 (개발 흐름 차단, 시연 리스크)
- **증상**: `uvicorn` 기동 시 "Loading pretrained ViT-B-32 weights" 로그를 마지막으로 프로세스가 **에러 메시지 없이** 사라짐(exit 5). pytest에서도 같은 지점(access violation). 같은 날 아침에는 정상 부팅했었음.
- **원인 규명** (가설을 하나씩 소거):
  1. *가중치 캐시 손상?* → HF 캐시 파일 크기·날짜 정상(577MiB, 재다운로드 흔적 없음). **기각.**
  2. *우리 코드 문제?* → 앱 코드 없이 CLIP만 단독 로드 → **성공**(151M 파라미터). **기각.**
  3. *faiss를 torch보다 먼저 import하는 순서 문제?* → 그 순서로 재현 시도 → 크래시 없음. **기각.**
  4. *DB 커넥션 풀?* → 무관 확인.
  5. 시스템 커밋 메모리 확인 → **25.5/29.8GB (여유 4GB 미만).** safetensors mmap+텐서 실체화 순간의 커밋 스파이크를 시스템이 못 받아줌 → 프로세스가 OS 레벨에서 즉사(그래서 파이썬 로그가 없음). RAM에 여유가 생긴 뒤 재시도하니 부팅 성공. **확정.**
- **조치/우회**: 무거운 프로세스(IDE Java LS, gradle 데몬, 다른 dev 서버) 정리 후 기동. 근본 해결은 **페이지파일 증설**(E: 드라이브에 16~24GB 추가) — 사용자 결정 대기.
- **검증**: 메모리 확보 후 동일 명령으로 부팅 성공, `/health` 200 (index 100 / DB 100).
- **교훈**: "로그 없이 죽는" 크래시는 파이썬 안이 아니라 **OS 자원(커밋 메모리)** 부터 의심하라. 그리고 아침에 되던 게 저녁에 안 되면 코드가 아니라 **환경의 변화**(동시 실행 프로세스)를 먼저 보라. 이 머신에서 `test_api_contract.py`(CLIP 로드)는 메모리 여유 확인 후 실행할 것.

## 양식 — 새 항목 작성 가이드

새 문제를 해결했으면 아래 템플릿을 복사해 **목차 표와 본문에 추가**한다. ID는 `TS-번호` 순번.

**언제 기록하나**: ① 30분 이상 잡아먹었다 ② 다른 팀원도 겪을 수 있다 ③ 외부 시스템(KIPRIS·DB·환경)의 문서에 없는 동작을 발견했다 — 셋 중 하나면 기록.

**심각도 기준**: `치명`(데이터 손실·서비스 오답) / `높음`(핵심 기능 차단·일정 영향) / `중간`(개발 흐름 차단·우회 존재) / `낮음`(불편·경고성).

```markdown
<a id="ts-NN"></a>
## TS-NN. (한 줄 제목 — 증상 기준으로, 원인 기준 아님)

- **날짜/해결자**: YYYY-MM-DD / 이름 · **심각도**: 치명|높음|중간|낮음
- **증상**: 무엇이 어떻게 잘못 보였나. 에러 메시지가 있으면 원문 그대로.
- **원인 규명**: 어떻게 좁혀갔나 — 세운 가설과 기각 근거까지 순서대로.
  (결론만 쓰지 말 것. "삽질 경로"가 다음 사람의 지름길이다)
- **조치**: 무엇을 바꿨나 (커밋 해시·파일 경로 포함하면 좋음)
- **검증**: 고쳐졌음을 어떻게 확인했나 (테스트·실측 수치)
- **재발 방지**: 테스트·가드·문서 등 (없으면 "없음 — 사유")
- **교훈**: 다음 사람이 기억할 한두 문장
```

- KIPRIS 실측 정보는 이 문서가 아니라 `MarkLens_백엔드6_데이터확장_수집기준_초안.md` 부록 A(오퍼레이션 명세)에 모은다 — 여기엔 링크만.
