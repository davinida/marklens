### 3. 로깅 + 요청 ID + 전역 예외 핸들러

지금까지 백엔드에 logging이 아예 없었다 (print 하나). 문제 생기면 추적할 방법이 없어서:

- stdlib `logging.dictConfig`로 uvicorn 로그까지 포맷 통일
- 요청마다 8자리 ID 발급 → 모든 로그 라인에 자동 주입 + 응답 `X-Request-ID` 헤더로 반환 (문의 들어오면 이 ID로 로그 대조)
- 미처리 예외는 전역 핸들러가 받아서 traceback은 로그로, 클라이언트에는 스택 없는 JSON 500만

loguru나 JSON 로그는 일부러 안 썼다 — 로그 수집기도 없는데 과잉이다.

### 4. /search 이벤트 루프 차단 해소 (성능 구조 결함)

`/search`가 async인데 안에서 CPU 작업(CLIP 인코딩+FAISS)과 동기 DB 쿼리를 그대로 돌리고 있었다 → 검색 1건 도는 동안 서버 전체(다른 사람 요청, /health까지)가 얼어붙는 구조. `anyio.to_thread` + `CapacityLimiter(2)`로 워커 스레드에 넘겼다 (동시 CLIP 2개 초과는 대기열 — CPU 스래싱 방지).

**실측: 검색 2건 동시 진행 중에 /health가 6~7ms로 응답.** 고치기 전엔 검색 끝날 때까지 블록이었다. KIPRIS 클라이언트도 호출마다 httpx.Client를 새로 만들던 걸 공용 클라이언트(커넥션 풀)로 바꿨다.

### 5. 마이그레이션 버전 추적 (schema_migrations)

migrate 스크립트가 매번 모든 *.sql을 재실행하며 멱등성에만 기대고 있었다. `schema_migrations` 테이블을 추가해 **미적용 파일만, 파일당 트랜잭션으로** 적용하게 바꿨다. 로컬 PostgreSQL에서 실검증: 2회 연속 실행 시 두 번째는 "0 applied". Alembic은 안 썼다 — ORM 모델이 없어서 autogenerate가 무용지물이고, 우리 raw SQL 방식엔 30줄 업그레이드가 맞다.

### 6. name-check 캐시 상한

수제 dict 캐시가 상한이 없어서 서로 다른 질의가 쌓이면 무한 성장하는 구조였다. `cachetools.TTLCache(maxsize=1024, ttl=24h)`로 교체. 이 캐시는 성능용이 아니라 **KIPRIS 월 1,000회 한도 보호 장치**라 실호출 시작 전에 고쳐야 했다.

### 7. 테스트 인프라 + CI

계약 테스트가 "인덱스 없으면 전부 skip"이라 새 클론이나 CI에서는 무용지물이었다. conftest에서 **더미 FAISS 인덱스를 인프로세스로 생성 + encode_image를 결정적 벡터로 몽키패치**하는 픽스처를 만들어 CLIP 가중치 다운로드 없이 어디서나 돌게 했다. 루트 pyproject.toml로 `pytest` 한 방에 백엔드+ml 전체 실행. GitHub Actions 워크플로도 작성했다 (torch는 CPU 휠 인덱스로 — 기본 리눅스 휠은 CUDA 포함 2GB짜리라 함정, postgres:16 서비스 컨테이너 포함).

**최종: 48 passed / 0 skipped** (실제 CLIP + db 모드 + 테스트 DB 전부 포함).

### 8. 백+프론트 통합 실행 스크립트

매번 터미널 2개 열고 uvicorn 규칙(반드시 루트에서) 기억해야 하는 게 번거로워서 한 방 스크립트를 만들었다:

- `scripts\dev-start.ps1` (맥용 `dev-start.sh`): 포트 8000/3000 선점 검사 → 백엔드 기동 → /health가 engine_ready 될 때까지 대기(CLIP 로딩) → 프론트 기동 → PID 기록. `-Force`로 점유 프로세스 정리 후 재시작 가능.
- `scripts\dev-stop.ps1` (`dev-stop.sh`): 기록된 PID + 포트 폴백으로 `--reload` 워커까지 프로세스 트리째 종료. python/node가 아닌 프로세스는 건드리지 않는 안전장치 포함.

시작→검색→종료 전체 사이클 실동작 확인했고 README §6-7에 사용법을 넣어뒀다.
