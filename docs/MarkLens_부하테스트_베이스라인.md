## 1. 왜 지금 측정하는가

9월 다축 확장(X1 호칭 / X3 관념 / X4 상품 견련성 + 통합 로지스틱 회귀)은 요청당
연산량을 늘린다. **확장 이후의 성능 회귀를 "수치로" 잡으려면, 확장 전 현재
백엔드의 응답 시간·처리량 기준점이 있어야 한다.** 이 문서는 그 기준점을 측정하는
절차와, 측정값을 남기는 **기록 템플릿**을 정의한다.

측정 도구는 locust 다(감사보고서 R13: k6/JMeter 대비 — 파이썬 팀 + multipart
업로드 시나리오가 단순 + CPU 바운드 한 자릿수 RPS 규모라 도구의 화려함보다
재현성이 중요). 시나리오는 **`/search` 5동시 + `/health` 1폴링**이다.

측정 대상 지표(회귀 판정 기준):
- `POST /search` 의 **p50 / p95 / RPS** — 다축 전 공식 베이스라인.
- 부하 중 `GET /health` 의 **p95 < 100ms** 유지 (검색이 이벤트 루프를 막지 않는지).
- **5xx = 0** (레이트리밋 429 는 5xx 가 아니며, 측정 무효 신호로 별도 집계).

## 2. 현재 상태: 미측정 (정직한 기록)

> **이 항목을 지우지 말 것.** 아래 3장의 기록 표는 실제 측정 전까지 비어 있다.

작성 시점(2026-07-09) 기준 **아직 실측하지 못했다.** 개발 머신의 여유 메모리가
빠듯해 CLIP 로딩이 간헐적으로 프로세스를 죽이는(OSError 1455 실측 이력, 기동
여유 ~4.5GB 요구 — 감사보고서 §3-1 참조) 환경이라, 모델을 실제로 띄운 채로
부하를 거는 측정을 신뢰성 있게 반복할 수 없었다. 따라서:

- 아래 **3. 측정 기록** 표는 전부 `미측정` 이다.
- 최초 실측은 메모리 여유가 있는 머신(또는 확장 전 마지막 시점의 안정 환경)에서
  수행하고, 그 커밋 해시·머신 메모와 함께 표에 한 줄을 채운다.
- 다축 확장(9월) 직후 동일 시나리오를 재측정해 회귀분을 비교한다.

## 4. 측정 절차

### 4-0. 준비 (설치는 측정할 때만)

locust 는 상시 의존성이 아니다. 측정 직전에만 설치한다.

```powershell
# 저장소 루트에서
.\ml\venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt
```

업로드 픽스처(`ml/data/queries/` 의 브랜드 로고 PNG)가 존재해야 한다. 없으면
locustfile 이 기동 즉시 명확한 오류로 실패한다.

### 4-1. 측정용 서버 기동 — 레이트리밋을 반드시 상향

> **가장 흔한 실수:** 기본 서버로 측정하면 `/search` 레이트리밋(기본 10/minute·IP)에
> 걸려 몇 초 만에 전부 429 로 튕긴다. 부하 테스트는 단일 IP 이므로 한도를 넉넉히
> 올려야 한다. 이는 **측정용 임시 상향**이며 운영/시연 기본값을 바꾸는 것이 아니다
> (측정 후 env 원복).

```powershell
# 서버 셸
$env:MARKLENS_SEARCH_RATELIMIT = "100000/minute"   # 측정용 임시 상향
# 하드닝(인증) 서버를 재현하려면 키도 설정 — 아래 클라이언트와 동일 값
# $env:MARKLENS_API_KEY = "<임의의 키>"
uvicorn backend.src.main:app
```

엔진 로딩(`/health` 가 `engine_ready: true`, `index_size > 0`)을 먼저 확인한 뒤
부하를 건다. 인덱스가 비어 있으면 `/search` 가 503 이라 측정이 무의미하다.

### 4-2. 부하 클라이언트 기동

```powershell
# 별도 셸. 서버에 키를 걸었다면 동일 키를 env 로 주면 헤더에 자동 부착된다.
# $env:MARKLENS_API_KEY = "<서버와 동일한 키>"
locust -f backend/tests/perf/locustfile.py --host http://127.0.0.1:8000 --headless -u 6 -r 2 -t 5m
```

- `-u 6` = 검색 5 + 헬스 1 (locustfile 의 `fixed_count` 합). 비율을 바꾸려면
  `MARKLENS_LOCUST_SEARCH_USERS` / `MARKLENS_LOCUST_HEALTH_USERS` env 로 조정.
- `-r 2` = 초당 2명 스폰(ramp-up), `-t 5m` = 5분 측정.
- 웹 UI 로 보려면 `--headless` 를 빼고 브라우저에서 `http://localhost:8089` 접속.

### 4-3. 결과 판독

- locust 요약의 `POST /search` 행에서 **p50(50%) / p95(95%) / Requests/s(RPS) /
  Failures** 를 3장 표에 옮긴다.
- **Failures 에 429 가 잡히면** 측정 무효 — 4-1 의 레이트리밋 상향을 빠뜨린 것이다.
  서버를 다시 띄우고 재측정한다. (locustfile 이 429/401/503 을 실패 사유 문자열로
  구분해 표시하므로 원인을 바로 알 수 있다.)
- **5xx 는 0 이어야 한다.** 발생 시 서버 로그의 `X-Request-ID` 로 원인을 추적한다.

## 5. 회귀 비교(9월 이후)

다축 확장 후 **같은 시나리오·같은(또는 동급) 머신**에서 재측정하고, 3장 표에
새 줄을 추가한다. 확장 전/후 p95 증가분이 곧 다축의 요청당 비용이다.

- `POST /search` p95 가 목표 SLO 를 넘기면 → 감사보고서 §"하지 말 것"의 순서에 따라
  먼저 프로파일링으로 병목 축을 특정하고, 그 다음에야 TorchServe/ONNX/GPU 를 검토한다
  (시연 규모에서는 CPU 로 충분하다는 것이 R13 이전까지의 결론).
- `GET /health` p95 가 부하 중 100ms 를 넘기면 → `to_thread` 오프로드 또는
  `CapacityLimiter` 설정이 회귀했는지 확인한다(감사보고서 §3-1).
