# MarkLens UI 평가 (2026-11-22)

기준: `main` = `develop` = `bf0b20b`(PR #105 손그림 실현성 평가 병합), 브랜치 `chore/ui-review`. 평가만 했고 화면 코드는
고치지 않았다. KIPRIS 호출 0, 의존성 변화 0(`package.json`·잠금 파일 그대로).

캡처는 비공개 DB 로고가 들어 있어 저장소 밖에 둔다: `~/marklens-archive/ui-review-20261122/`
(`desktop-1440/`·`phone-390/`·`present-1920/` 상태별 PNG, `responses/` 재사용한 응답, `lighthouse/`, `capture_report.json` —
상태마다 axe 결과·가로 넘침·콘솔 오류, `tools/capture.mjs` 캡처 도구).

## 1. 요약

- 입력 화면은 대체로 잘 돌아간다. 로고 영역 선택, 업종 세트 한 번에 추가, OCR 로 읽은 상표명 넣기와 "틀린 부분이 있으면 고쳐 주세요" 안내,
  파일 오류 문구가 분명하고, 390px 에서도 가로 넘침이 없다.
- 결과 화면은 등급의 뜻과 근거가 흔들린다(P0 3건).
  - 지어낸 상표명만 넣어도 전체 등급이 늘 '검토 권장' 이상이다.
  - '위험' 카드의 근거 문구가 "검토 권장으로 올렸습니다"라고 말한다.
  - 로고만 비교한 판단에 "여러 축이 비슷한 선행 상표가 있습니다"가 붙는다.
- 그 밖에 결과가 나와도 화면 낭독기에 알림·포커스가 없다. 유형을 고친 뒤 입력 화면에 바뀐 유형이 보이지 않는다.
  휴대폰에서는 후보 카드의 축 칩이 한 줄에 하나씩 쌓인다. 발표 화면(1920×1080)에서는 등급·위험도가 13px 이라 뒷자리에서
  읽기 어렵다. 이 넷이 P1 이다.
- 검사 도구 결과
  - **axe:** critical 1종(라벨 없는 파일 입력) · serious 1종(검토 권장·안전 설명 글씨 대비 4.43·4.07) · moderate 2종(결과 화면 h1 없음, 제목 단계 건너뜀).
  - **Lighthouse(프로덕션 빌드):** 휴대폰 성능 75·접근성 95·모범 사례 93, 데스크톱 90·95·96. 휴대폰 LCP 12.3초는 2,011KiB 글꼴 한 파일 때문이다.
  - **AI 티:** 정한 디자인 체계('토스 결' 토큰)를 따르고 있어 거의 없다.
  - **한국어 문구:** 결과 화면만 합니다체(12곳)이고 나머지는 해요체이며, 조사 오류가 몇 곳 있다.

## 2. 방법

- 서버
  - 실제 모델 백엔드(`bash scripts/dev-start.sh`)를 띄웠다. 환경 변수로만 `KIPRIS_ACCESS_KEY`·`KIPRIS_TRIAL_ACCESS_KEY` 를 비우고(혹시 불려도
    KIPRIS 까지 가지 않게), 검색·이미지·발음·관념·상품 한도를 600–6000/분으로 올렸다. 파일은 고치지 않았다.
  - 프런트는 `next dev`(3000)다. 성능 측정만 같은 코드의 프로덕션 빌드(`next start`, 3100)로 따로 했다.
- 입력
  - 정상 상태는 실제 모델과 시연 시나리오 입력이다. 이름+이미지+업종은 BLU hands 로고 + "블루커피" + 카페 세트, 로고만은 BLU hands, 사진은 칠우불고기
    간판 사진 + "칠우불고기", 비슷한 후보 없음은 DB 밖 심결 표장(전체 안전·가까운 후보 없음), 아주 긴 상표명은 66자 이름 + 카페 세트를 썼다.
  - 상표명 확인 패널의 KIPRIS 응답은 E2E 모의 응답(`frontend/e2e/marklens.spec.ts` 의 `NAME_CHECK_RESULT`)을 썼다. 발음·관념 목록은 실제 백엔드다.
  - 429·502 는 E2E 에 모의 응답이 없어서, 백엔드 `rate_limit_exceeded_handler`·BFF `jsonError` 가 실제로 주는 본문 형식에 Vitest 픽스처의
    헤더 값(`retry-after: 30`)을 붙였다.
- 폭: 데스크톱 1440×900, 휴대폰 390×844(DPR 2·터치), 발표 1920×1080(전체 페이지와 첫 화면을 따로 찍음). 1440 에서 받은 응답을 390·1920 에서
  그대로 다시 썼고, 다시 쓰지 못한 요청은 0건이다.
- 다크 모드: 지원하지 않는다. CSS 에 다크 규칙이 없고, 다크 설정으로 찍은 빈 화면이 밝은 화면과 바이트까지 같다.
- 도구
  - axe-core 4.12.1: `node_modules` 에 있던 것을 Playwright 로 상태마다 주입했다.
  - Lighthouse 12.8.2: `npx` 로 받았고, 설치하지 않았다(npm 캐시).
  - `avoid-ai-design` 스킬: 감지 모드로만 썼다.
  - jungrok5/ai-design `style_check.py`(커밋 `0da8a1d1`): 설치 없이 그 파일과 `rules.toml` 만 받아 Python 3.11 로 돌렸다.
- 사용성 점수: 캡처를 직접 보고 1–5점(5 매우 좋음)을 매겼다. 평가자 한 명의 휴리스틱 평가이며, 사용자 시험은 아니다.

## 5. 검사 결과

### 5-1. axe-core 4.12.1(상태 19 × 폭 3)

| 등급 | 규칙 | 상태 | 대상과 내용 |
|---|---|---|---|
| critical | `label` | 입력 9개 상태 × 세 폭 | `input[type="file"]` — 화면에 안 보이는(sr-only) 파일 입력에 라벨이 없다 |
| serious | `color-contrast` | I07·R02·R04·R05·R08 | 검토 권장 설명 `#a96000` / `#fff4e5` 4.43:1, 안전 설명 `#6b7684` / `#eef1f4` 4.07:1(기준 4.5:1) |
| moderate | `page-has-heading-one` | 결과 6개 상태 | 결과 화면에 h1 이 없다. 실측하니 결과가 나온 뒤 포커스가 `BODY` 에 있고 live region 도 0개였다(Tab 한 번에 "도형로 고치기") |
| moderate | `heading-order` | R02 | 펼친 근거의 h4("등급 근거 축")가 h2 다음에 온다 |

그 밖의 등급 색 대비는 위험 설명 4.78, 주의 설명 4.74, 흰 글씨 알약 4.62–5.42 로 기준을 겨우 넘는다. 프로젝터에서는 흐려지기 쉽다.

### 5-2. Lighthouse 12.8.2(첫 화면)

| 서버 | 설정 | 성능 | 접근성 | 모범 사례 | FCP | LCP | 첫 화면 전송량 |
|---|---|---:|---:|---:|---:|---:|---:|
| 개발(`next dev`) | 휴대폰 | 72 | 95 | 96 | 2.3초 | 17.7초 | 3,060KiB |
| 개발(`next dev`) | 데스크톱 | 83 | 95 | 100 | 0.2초 | 3.0초 | 3,060KiB |
| 프로덕션 빌드 | 휴대폰 | 75 | 95 | 93 | 0.9초 | 12.3초 | 2,253KiB |

- 휴대폰 LCP: LCP 요소는 머리글 "MarkLens" 글자이고 96%가 렌더 지연이다. 첫 화면 전송량의 89%(2,011KiB)가 `PretendardVariable.woff2` 한 파일이라,
  느린 망에서 글꼴이 다 내려온 뒤 글자가 다시 그려진다.
- 접근성 95: 위의 라벨 없는 파일 입력과 휴대폰 "읽기 쉬운 글자 크기" 55%(11px 34.5%·11.5px 11.2%)가 깎였다.
- 모범 사례: 프로덕션 휴대폰에서 Chrome Issues 패널에 CSP 항목 1건이 잡혔다. 콘솔 오류는 0건이고 원인은 확인하지 못했다.
- 개발 서버 수치는 압축하지 않은 JS 를 쓰므로 참고용이다.

### 5-3. AI 티(`avoid-ai-design` 감지 모드)

이 화면은 정한 디자인 체계를 따른다(`app/globals.css` 의 'E안 토스 결' 토큰 — 회색 바탕에 흰 카드, 파란 단일 액션 색, 예약된 등급 색, 글꼴 Pretendard).
그래서 프로필을 `inside-design-system` 으로 보고 판단했다.

스캐너는 39개 파일에서 P0 2·P1 4·P2 8건을 찾았고, 파일별 겹친 흔적은 최대 2개였다(6개 이상이면 틀에서 찍은 것으로 본다).

| 흔적 | 위치 | 판단 |

- 문제: 등급 알약·위험도가 13px, 축 칩이 11px 이고 화면 절반이 빈 공간이다. 입력 첫 화면에서는 제출 버튼이 잘린다.
- 왜 문제인가: 프로젝터 뒷자리에서 등급·숫자가 읽히지 않는다.
- 근거: `present-1920/*__viewport.png`.
- 고치는 방향: 결과 머리의 등급·위험도를 28–32px 로 키운다. 넓은 화면에서는 머리 카드를 두 칸(왼쪽 등급·숫자, 오른쪽 설명)으로 나눈다. 입력 화면은 넓은 화면에서 두 칸으로 해 제출 버튼을 첫 화면 안에 둔다.
- 바꿀 파일: `frontend/components/ResultViewV2.tsx`(지원님 결과 화면), `frontend/app/page.tsx`, `SearchForm.tsx`.
- 크기: M.

**P1-7. 라벨 없는 파일 입력**
- 화면·상태: 입력 전반.
- 문제: 화면에 안 보이는 파일 입력에 라벨이 없다.
- 왜 문제인가: 화면 낭독기가 이름 없는 파일 입력을 읽는다.
- 근거: axe critical `label`(9개 상태), Lighthouse 접근성.
- 고치는 방향: 버튼이 대신 열어 주므로 `aria-hidden` 을 주거나 `aria-label="로고 이미지 파일"` 을 단다.
- 바꿀 파일: `frontend/components/SearchForm.tsx`.
- 크기: S.

**P1-8. 등급 설명 글씨 대비 부족**
- 화면·상태: 검토 권장·안전 결과, 상표명 확인 패널.
- 문제: 검토 권장 설명 4.43:1, 안전 설명 4.07:1 이다.
- 왜 문제인가: 기준(4.5:1) 미달이고 프로젝터에서 더 흐려진다.
- 근거: axe serious `color-contrast`(5개 상태), 토큰 대비 계산.
- 고치는 방향: `--review-deep` 를 조금 더 어둡게(약 #995600) 하고, 안전 설명은 `--sub` 로 쓴다.
- 바꿀 파일: `frontend/app/globals.css`, `frontend/components/ResultViewV2.tsx`(지원님 결과 화면).
- 크기: S.

**P1-9. 429 안내가 영어·합니다체이고 기다리라는 시간을 지키지 않음**
- 화면·상태: 한도 초과(R06).
- 문제
  - "요청이 너무 많습니다. 잠시 후 다시 시도하세요. (허용 한도: 10 per 1 minute)"가 그대로 나온다.
  - "다시 시도 가능: 30초 후"는 고정 문구이고, 버튼은 바로 눌린다.
- 왜 문제인가: 사용자가 바로 다시 눌러 또 429 를 만난다.
- 근거: R06 캡처, 백엔드 `rate_limit_exceeded_handler`.
- 고치는 방향: 백엔드 문구를 "요청이 많아요. 30초 뒤에 다시 해 주세요."처럼 해요체로 바꾸고 한도 문자열을 뺀다. 화면은 Retry-After 동안 남은 초를 보이고 버튼을 잠근다.
- 바꿀 파일: `backend/src/core/ratelimit.py`, `frontend/components/ErrorView.tsx`.
- 크기: S.

**P1-10. 사진 안내가 눈에 띄지 않음**
- 화면·상태: 사진 안내(R04).
- 문제: "사진으로 보여요 — 로고 파일을 올리면 외관 비교가 더 정확해요"가 11px 회색 목록 한 줄이다.
- 왜 문제인가: 사진으로 찾은 결과의 한계를 모르고 결과를 믿게 된다.
- 근거: R04 캡처.
- 고치는 방향: 사진 판정이면 머리 카드에 아이콘이 있는 안내 상자와 "로고 파일로 다시 하기" 버튼을 둔다.
- 바꿀 파일: `frontend/components/ResultViewV2.tsx`(지원님 결과 화면).
- 크기: S.

**P1-11. 결과 화면에 무엇을 검색했는지가 없음**
- 화면·상태: 결과 전반(R01·R08).
- 문제: 상표명·지정상품 수가 결과 화면에 없다. 상표명만 검색하면 머리 카드에 질의 정보가 하나도 없다.
- 왜 문제인가: 사용자(특히 발표 청중)가 결과가 무엇에 대한 것인지 확인할 수 없다.
- 근거: R08 캡처.
- 고치는 방향: 머리 카드에 "'블루커피' · 로고 · 지정상품 3개" 요약 줄을 넣는다.
- 바꿀 파일: `frontend/components/ResultViewV2.tsx`(지원님 결과 화면), `frontend/app/page.tsx`(질의 정보 전달).
- 크기: S.

**P1-12. 근거 막대·등급 눈금에 수치·라벨이 없음**
- 화면·상태: 결과 머리·근거 펼침(R01·R02).
- 문제
  - 등급 눈금에 등급 이름이 없다.
  - 근거 막대에 비율이 없다.
  - 관념 91% 인데 관념 막대가 없다(기여 0이라 빠짐).
- 왜 문제인가: 왜 그 등급인지 설명이 반쯤 끊긴다.
- 근거: R01·R02 캡처.
- 고치는 방향: 눈금 아래 등급 이름 네 개를 쓴다. 막대 옆에 크기 말("크게"·"조금")이나 비율을 쓴다. 기여가 0인 축은 "판단에 쓰지 않음"으로 보인다.
- 바꿀 파일: `frontend/components/ResultViewV2.tsx`(지원님 결과 화면).
- 크기: S–M.

**P1-13. 참고 정보라는 안내가 결과 맨 아래 10.5px 에만 있음**

- 문제: 머리 카드는 '위험'을 크게 보이는데, "법적 판단이 아닙니다"는 맨 아래 작은 글씨다.
- 왜 문제인가: 등급을 법적 결론으로 읽을 수 있다.
- 근거: 캡처.
- 고치는 방향: 머리 카드 등급 옆이나 아래에 "참고 정보 · 법률 판단 아님" 한 줄을 둔다.
- 바꿀 파일: `frontend/components/ResultViewV2.tsx`(지원님 결과 화면).

## 7. 손그림 그리기 영역의 위치

손그림 실현성 평가(X2 설계 §10 6, 판정 진행·방법 B 윤곽선 색인)를 이어, 입력 화면에 그리기를 넣을 자리를 세 가지로 견줬다. 지금 입력 화면은
위에서부터 제목 → 로고 이미지 → 상표 이름 → 지정상품 → 결과 개수 → 자동 요청 확인 → 제출이다.

**A안. 로고 카드 안 탭 — "이미지 올리기 | 직접 그리기(실험)"**
- 장점
  - 로고 한 칸에 이미지나 그림 중 하나만 넣는 구조라 API 의 이미지 입력 하나와 맞는다.
  - 화면 길이가 늘지 않고, 맨 위라 눈에 띈다.
- 단점
  - 탭에 가려 실험 기능이 덜 보이거나, 반대로 실험 기능이 주 입력과 같은 무게로 보인다.
  - 휴대폰에서 카드 안 캔버스(약 350px)는 좁다. 그리는 손짓과 페이지 스크롤이 부딪힌다(`touch-action: none` 필요).

**B안. 로고 카드 아래 "로고 파일이 없나요? 직접 그려 보기(실험)" → 전체 화면 그리기 창**
- 장점
  - 휴대폰에서 화면 전체를 캔버스로 써 그리기 쉽고 스크롤과 부딪히지 않는다.
  - 지금 쓰는 로고 영역 선택 대화상자의 흐름(적용·취소 → 미리보기)을 그대로 쓴다.
  - 입력 화면이 길어지지 않고 '실험'임이 분명하다.
- 단점
  - 링크가 작으면 잘 안 보인다. 데스크톱에서는 창이 무겁게 느껴질 수 있다.
  - 그린 뒤 고치려면 창을 다시 열어야 한다.

**C안. 별도 카드로 늘 펼쳐 둠(상표 이름 카드 앞)**
- 장점: 가장 잘 보이고, 발표에서 바로 그려 보이기 좋다.
- 단점
  - 이미 긴 화면이 더 길어져 제출 버튼이 더 멀어진다.
  - 로고 이미지와 그림 둘 다 넣으면 무엇을 쓰는지 정해야 한다.
  - 휴대폰 페이지 가운데에서 스크롤과 그리기가 부딪힌다. 실험 기능치고 너무 앞에 선다.

추천은 B안이다. 휴대폰 사용과 실험 기능이라는 성격에 맞고, 기존 대화상자 흐름을 그대로 쓴다. 발표에서 눈에 띄어야 하면 데스크톱에서만 A안 탭을 함께
보이는 방법이 있다. 어느 안이든 실현성 평가와 같은 처리를 따라야 한다.
- 그린 획은 흰 바탕·검은 선, 512px 캔버스에서 굵기 5px 로 맞춘다.
- 여백을 자르고 정사각형으로 패딩한다.
- 같은 평가의 낙서 잉크 비율(중앙값 3.0%, 5–95% 1.0–5.4%)을 "그림이 너무 비었어요" 같은 1단계 검사 기준 후보로 쓸 수 있다.

## 8. 한계

- 개발 서버 화면이라 왼쪽 아래에 Next.js 개발 표시("N")가 찍혔다. 자동 요청 확인 칸에는 "개발용 자동 요청 확인이 적용됐어요."가 나온다(운영에서는
  Turnstile 위젯). 평가에서는 둘 다 뺐다.
- 상표명 확인(KIPRIS) 결과는 E2E 모의 응답이다. 실제 KIPRIS 응답의 길이·문구는 다를 수 있다.
- 프로젝터 가독성은 1920×1080 화면 크기로만 판단했다. 실제 프로젝터·좌석 거리로 재지 않았다.
- 점수는 평가자 한 명의 휴리스틱 평가다. 실제 사용자 시험(과제 수행·말하며 생각하기)은 하지 않았다.
- P0-1 은 화면이 아니라 통합 모델의 등급 하한에서 나온다. 화면으로는 근거를 보이게 하는 데까지만 고칠 수 있다.
